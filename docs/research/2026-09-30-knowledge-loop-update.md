# 2026년 측정치가 지식 루프의 게이트를 다시 그린다

1차 리서치의 큰 방향(하네스 위에 얇게 얹는 규약, 승격 조건부 인덱스, 위키는 사람 채택·스킬은 검증된 성공)은 2026년 상반기 이후의 통제 측정으로 대체로 강화되었지만, 게이트의 위치와 형태가 네 곳에서 바뀐다. 첫째, 경험을 지식으로 컴파일하는 작업은 세션마다 돌리면 안 된다. 정답 궤적만으로 통합해도 이전에 100% 풀던 문제의 54%를 다시 틀리고, 유효 상태가 없는 append-only 메모리는 드리프트 아래에서 메모리 없음(0.309)보다 낮은 0.210을 기록한 반면 명시적 폐기 상태를 둔 설계는 0.950을 냈다 ([arXiv 2605.12978](https://arxiv.org/html/2605.12978); [arXiv 2608.07429](https://arxiv.org/html/2608.07429v1)). 통합은 배치로, 폐기는 프론트매터의 명시 상태로 간다. 둘째, 스킬은 절차만 엔진을 건넌다. Codex에서 최적화한 스킬이 Claude Code의 SpreadsheetBench를 22.1에서 81.8로 끌어올렸지만 수학 추론 스킬은 이득의 약 10%만 남았으므로 ([arXiv 2605.23904](https://arxiv.org/abs/2605.23904)), SKILL.md에는 명령·검사·출력 형식만 쓰고 추론 휴리스틱은 뺀다. 셋째, 사람의 검토는 예산이다. 한 세션에서 50회를 넘긴 뒤 위험 명령 차단율이 17%에서 5%로 떨어진 Anthropic의 측정은 ([claude.com](https://claude.com/blog/auto-mode-default-in-claude-code)) 결정 인박스를 로그가 아니라 상한이 있는 필터로 만들 것을 요구한다. 넷째, 측정은 통과율이 아니라 카운트로 한다. VibeMemBench는 111개 표본에서 1.1~4.5점의 이득을 보고도 다섯 신뢰구간이 모두 0을 지났으므로 ([arXiv 2609.23570](https://arxiv.org/pdf/2609.23570)), 1인 개발자의 한 분기 표본으로 통과율 개선을 확인하는 일은 불가능하고, 에피소드당 교정 횟수와 실패 서명 재발이 실질 지표가 된다. 한국어 검색에서는 토크나이저가 어떤 작성 규약보다 큰 레버라는 데이터가 확인되어(기본 정규식 토크나이저 Recall@10 0/10, 바이그램 10/10) ripgrep 시절의 질의 규칙과 인덱스 도입 시 체크리스트가 정해졌다. 2부는 이 수정 위에서 다음 한 분기의 4단계 기획안과, 채택하지 않을 것의 목록을 낸다.

근거 등급은 1차와 같이 **측정**(통제 실험·벤치마크·재현 가능한 로그 수치), **벤더**(개발 주체의 자체 보고·공식 문서), **일화**(단일 실무자·이슈 스레드)로 표시한다. 2차 자료만 확인된 수치는 **2차**로 따로 적고 설계 결정의 단독 근거로 쓰지 않는다.

# 1부. 최신 근거로 본 수정 사항

## 통합은 세션마다가 아니라 배치로, 그리고 원본 에피소드를 남기고 한다

1차는 `SessionEnd` 훅이 세션마다 요약을 `inbox/`에 적는 경로를 권했고 그 자체는 유지되지만, 그 요약을 곧바로 위키에 합치는 일은 금지 항목이 된다. "Useful Memories Become Faulty When Continuously Updated by LLMs"는 ARC-AGI에서 정답으로 확인된 해법만 통합해도 **GPT-5.4가 이전에 100% 풀던 문제의 54%를 실패**했고, 결함은 입력 궤적이 아니라 추상화 단계에서 생겼다고 보고한다. 메모리 효용은 단조 증가하지 않고 ScienceWorld에서 약 20스텝에 정점을 찍은 뒤 100스텝까지 내려가며, WebShop의 메모리 정확도는 8개 예시에서 0.64였다가 128개에서 0.20으로 떨어졌다. 매 라운드 통합(Force)과 모델 재량(Auto), 에피소드만 유지(Episodic-only)를 비교하면 에피소드 전용이 강제 통합의 **정확도 두 배**였고, Auto 에이전트는 기본적으로 에피소드를 보존했다 ([arXiv 2605.12978](https://arxiv.org/html/2605.12978), 측정). 저자들의 권고인 "원본 에피소드를 1급 증거로 두고 추상화를 명시적으로 게이트하라"는 git 정본 구조에 그대로 옮겨진다. 하네스가 이미 남기는 전사와 `inbox/` 노트가 에피소드 층이고, 위키와 SKILL.md가 통합 층이며, 통합은 제자리 재작성이 아니라 제안된 diff다.

같은 방향의 두 번째 측정은 유효 상태다. TEPA는 "메모리 오염"을 새 증거에 의해 대체되었는데도 활성인 메모리가 주는 성능 저하로 정의하고, 50개 시드의 통제 드리프트에서 **append-only 0.210, last-write-wins 0.210, 메모리 없음 0.309, 유효성을 폐기 가능한 명시 상태로 둔 TEPA 0.950**을 기록했다. 파일 기반 실행 드리프트에서도 0.203 대 0.950으로 같은 구도였다 ([arXiv 2608.07429](https://arxiv.org/html/2608.07429v1), 측정). 이 수치는 1차의 "위키는 절대 롤백하지 않는다"를 수정한다. 파일을 지우지 않는다는 뜻은 유지되지만, `status: superseded`가 검색과 카탈로그에서 실제로 존중되지 않으면 그 위키는 append-only 메모리와 같은 것이고 메모리 없음보다 나쁘다. 그러므로 `index.md`는 `superseded`와 `deprecated`를 기본 목록에서 빼고, 에이전트 지침은 적용 전 `superseded_by`를 따라가도록 하며, 통합 패스가 충돌을 발견하면 추가가 아니라 supersession 편집을 제안한다. Codex Desktop에서 전역·저장소 AGENTS.md가 모두 로드됐는데도 에이전트가 영구 메모리의 낡은 워크플로를 따랐다는 이슈 #39223은 ([openai/codex](https://github.com/openai/codex/issues/39223), 일화) 두 권위가 병존할 때 벌어지는 일의 실사례이며, Markdown in git을 유일 정본으로 두고 엔진 측 메모리 기능을 끄는 제약이 정당한 이유다.

Anthropic이 2026년 5월 관리형 에이전트에 공개한 Dreaming도 방향을 확인해 준다. 세션 사이에 배치로 돌며 중복을 합치고 낡은 항목을 지우고 결과를 "승인·거부·수정" 가능한 층으로 내놓는 구조로, 개발자가 자동 적용과 수동 검토 중 고를 수 있다 ([Techzine](https://www.techzine.eu/news/devops/141125/anthropic-introduces-dreaming-for-claude-managed-agents/), 벤더·2차). 이 제품은 관리형 에이전트 전용이어서 채택 대상이 아니지만, "배치 통합 + 사람 승인"이 벤더 기본값이라는 점은 1차의 위키 게이트를 강화한다. 단 한 가지는 정직하게 적어야 한다. 사람 게이트가 좋은 자동 게이트보다 낫다는 통제 비교는 2026년 문헌에 없다. 측정된 것은 검증 분할이나 검증기 없는 자동 게이트가 유해한 편집을 들여보낸다는 것과, 보류 검증기를 가진 자동 게이트가 사람 저작을 따라잡거나 앞선다는 것이다 ([arXiv 2604.01687](https://arxiv.org/html/2604.01687v1); [arXiv 2605.27366](https://arxiv.org/html/2605.27366v1), 측정). 위키에 사람 게이트를 두는 근거는 "더 낫다"가 아니라 결정론적 평가 하네스가 없는 층에 대한 값싼 보험이라는 것이고, 스킬 층에 자동 게이트를 허용하는 근거는 거기에만 실행 가능한 검증기가 있다는 것이다.

| 1차 결론 | 2차 판정 | 근거 등급 |
| --- | --- | --- |
| `SessionEnd` 훅으로 세션마다 `inbox/` 요약 | 유지. 단 이것은 에피소드 층이며 위키 통합은 아님 | 측정(Faulty Memories) |
| 위키는 롤백하지 않음 | 수정. 파일은 남기되 `superseded`가 카탈로그·검색·지침에서 실제로 배제되어야 함 | 측정(TEPA) |
| 통합 시점 미지정 | 신설. 통합은 주 1회 배치, 한 배치가 한 PR, 제자리 재작성 금지 | 측정(Faulty Memories) + 벤더(Dreaming) |
| 위키 게이트 = 사람 채택 | 유지. 근거는 "자동보다 낫다"가 아니라 검증기 부재 층의 보험 | 측정 부재를 명시 |

## 스킬 승격은 통과가 아니라 무회귀·쌍대 비교·비용 상한으로 판정한다

1차의 스킬 규칙 "검증된 성공 + 대조 증거"는 두 방향에서 조여진다. 첫째, 성공만 보면 회귀를 놓친다. "Safe Harness Self-Evolution"은 실패했던 태스크에서의 이득이 이전에 성공했던 태스크의 보존을 보장하지 않음을 보이고 두 집합을 함께 보는 채택 조건을 제안했다 ([arXiv 2609.08175](https://arxiv.org/abs/2609.08175), 측정·이론). 위의 54% 회귀가 그 구체 사례다. 둘째, 새 코딩 스킬의 사전 확률은 낮다. SWE-Skills-Bench는 고정 커밋의 실제 저장소 565개 인스턴스에서 공개 SWE 스킬 49개를 결정론적 검증으로 재고 **39개가 통과율 개선 0, 평균 이득 +1.2%**, 7개가 최대 +30%, 3개가 최대 -10% 저하, 토큰 오버헤드는 통과율 변화 없이 최대 **451% 증가**까지 있었다고 보고했다. 저하 원인은 "버전이 어긋난 지침이 프로젝트 맥락과 충돌"한 것이었다 ([arXiv 2603.15401](https://arxiv.org/abs/2603.15401), 측정). 통과만 보는 게이트는 중립이면서 토큰만 먹는 스킬을 통과시킨다.

이 둘을 게이트로 옮기는 장치는 발표된 시스템들에 이미 있다. SkillAudit은 같은 태스크를 후보 스킬 유무로 쌍대 실행해 라벨 없이 인과 효과를 분리하고, 구조 검증기가 해로운 갱신을 롤백한다 ([arXiv 2606.14239](https://arxiv.org/abs/2606.14239), 측정). SkillOpt는 별도 옵티마이저가 SKILL.md 하나에 "경계 있는 add/delete/replace 편집"만 제안하고 검증 점수가 엄격히 오를 때만 수락하며 거부된 편집 버퍼를 둬 같은 편집이 재제안되지 않게 한다. 최종 산출물은 1~4개 편집이 누적된 379~1,995토큰 파일 하나로, 팽창에 하드 바운드가 걸린다 ([arXiv 2605.23904](https://arxiv.org/abs/2605.23904), 측정). "Rethinking Self-Evolving Agent Skills"는 5개 벤치마크·3개 모델·42회 피드백 실행에서 **388개 후보 중 55개만 바이트 단위로 구별되는 검증 최고점**을 세웠고, 검증 기반 선택이 고른 11개 스킬은 **전부 실패 궤적을 포함한 피드백 조건**에서 나왔다고 보고했다 ([arXiv 2608.02636](https://arxiv.org/pdf/2608.02636), 측정). 1차의 "대조 증거" 요건은 이 결과로 직접 지지되고, 동시에 "제안의 대부분은 거부되어야 정상"이라는 보정도 얻는다. 후보를 대부분 통과시키는 승격 규칙은 잘못 보정된 것이다.

무엇이 스킬을 망치는지도 구체적이다. MUSE-Autoskill에서 한 궤적에 과적합한 스킬은 hvac-control을 80%에서 20%로 떨어뜨렸고, 생성 스킬은 사람 스킬보다 2.2배 길었다(중앙값 326줄 대 146줄) ([arXiv 2605.27366](https://arxiv.org/html/2605.27366v1), 측정). 코딩 메모리 전이 연구는 6개 벤치마크 통합 풀에서 평균 +3.7%의 이득이 "검증 루틴 같은 메타 지식" 전이에서 왔고 "저수준 궤적은 과도한 구체성 때문에 부정 전이를 일으킨다"고 했다 ([arXiv 2604.14004](https://arxiv.org/pdf/2604.14004), 측정). 실제 개발자 세션 206개에서 채굴한 개인화 스킬 연구는 개인화 스킬이 "작고 일관되지 않은" 이득만 주고 여러 개발자를 합친 일반 스킬이 가장 크고 일관된 이득을 냈다고 보고했다 ([arXiv 2608.10319](https://arxiv.org/pdf/2608.10319), 측정). 종합하면 후보 SKILL.md에서 하드코딩된 경로·버전 핀·수치 상수를 잡는 lint 하나가 문서화된 두 저하 메커니즘을 모두 겨냥하고, 스킬은 "내 취향"보다 "검증 절차"를 담을 때 남는다.

스킬 라이브러리의 유지 관리는 거의 LLM 호출 없이 된다. SkillOps는 스킬당 효용(최근 태스크 중 그 스킬로 성공한 비율)·중복·호환·실패 위험·검증 공백의 다섯 신호와 merge·repair·retire·add_validator·add_adapter·instantiate 여섯 연산을 정의하고, 200개 스킬의 ALFWorld 절제에서 **전체 79.5%, 유지 루프 없음 71.9%, add_validator 없음 38.0%**를 기록했으며 유지는 본문 해시 충돌·효용 로그·타입 불일치 같은 규칙으로 패스당 3~9회 LLM 호출로 끝났다 ([arXiv 2605.13716](https://arxiv.org/html/2605.13716v1), 측정). 하네스가 전사를 남기므로 스킬별 호출·성공·마지막 사용은 통합 시점에 계산할 수 있고 데몬이 필요 없다.

| 1차 결론 | 2차 판정 | 근거 등급 |
| --- | --- | --- |
| 승격 = 검증된 성공 + 대조 증거 + 반복 | 유지하고 확장: (a) 유무 쌍대 비교에서 개선, (b) 이전 통과 평가가 두 엔진에서 모두 유지, (c) 실패 궤적이 편집을 동기화, (d) 경계 있는 diff + 하드코딩 lint 통과, (e) 토큰 비용 상한 이내 | 측정(SkillAudit, SkillOpt, Feedback Dynamics, SWE-Skills-Bench, MUSE) |
| 유지 카운터 `uses`/`downvotes` | 유지. 스킬 장부에 기록하고 SkillOps식 효용·중복 규칙으로 retire 제안 | 측정(SkillOps) |
| 롤백 = 재발 시 되돌림 | 확장: 거부·롤백 편집을 장부에 남겨 재제안을 막음 | 측정(SkillOpt 거부 버퍼) |
| 개인 세션에서 스킬 채굴 | 하향. 일반 절차 우선, 개인 선호는 반복·다중 예시가 있을 때만 | 측정(개인화 스킬 연구) |

## 절차는 엔진을 건너고 추론 휴리스틱은 건너지 못한다

엔진 중립 제약에 가장 직접적인 2026년 수치는 SkillOpt의 교차 하네스 셀이다. Codex 안에서 최적화한 스킬을 Claude Code에 넣었을 때 SpreadsheetBench가 **22.1에서 81.8**로 올라 Claude Code가 자기 하네스에서 최적화해 얻은 80.4보다 약간 높았고, 같은 전이가 LiveMath에서는 40.8에서 42.4로 도메인 내 이득의 약 10%만 남겼다. GPT 계열 안에서도 GPT-5.4-mini는 이득의 82%를, nano는 16%만 보존했다. 저자들의 요약은 "검사·검증·서식 워크플로 같은 절차 스킬은 효과적으로 전이되고" 수학 추론 스킬은 "학습 환경에 더 묶여 있는 것으로 보인다"이며, 한 GPT 계열과 축당 두 벤치마크라는 한계를 명시했다 ([arXiv 2605.23904](https://arxiv.org/abs/2605.23904), 측정; 셀별 수치는 [MarkTechPost](https://www.marktechpost.com/2026/08/05/microsoft-skillopt-agent-skill-transfer-portability/) 2차). EvoSkills는 Claude Opus 4.6에서 진화한 스킬이 다른 6개 LLM을 +35~44pp 올렸고, 호출 가능한 함수를 가진 206줄 스킬이 1,096줄 사람 스킬(53.5%)을 100%로 앞섰다 ([arXiv 2604.01687](https://arxiv.org/html/2604.01687v1), 측정).

설계 결정은 셋이다. SKILL.md는 실행할 명령, 확인할 검사, 출력 형식만 담고 모델별 추론 요령은 넣지 않거나 표시된 별도 절에 격리한다. 승격 평가는 저작한 엔진만이 아니라 Claude Code와 Codex 둘에서 돈다. 그리고 산문 위키 노트가 엔진을 건넌다는 측정은 어디에도 없으므로, 위키의 전이 가능성은 여전히 추론이고 실행자에게 위키를 직접 주지 않는 1차의 역할 분리가 그 불확실성을 흡수한다.

## 사람의 검토는 예산이며 50회를 넘으면 사실상 소진된다

1차는 사람 채택을 게이트로 두면서 그 비용을 다루지 않았다. Anthropic이 auto mode를 기본값으로 바꾸며 공개한 1,053명 테스트 데이터는 사람이 심어 둔 위험 명령의 **13.6%**를 차단한 반면 분류기는 89%를 차단했고, 사람의 차단율은 세션 초반 약 17%에서 **50회 이상 프롬프트 뒤 약 5%**로 떨어졌으며 분류기는 평평했다. 사용자는 권한 프롬프트의 97%를 승인했다 ([claude.com](https://claude.com/blog/auto-mode-default-in-claude-code), 벤더 측정·독립 재현 없음). 같은 데이터를 분석한 실무자는 계획 거부율이 39%인데 개별 명령 거부율은 3%라고 지적했다 ([yage.ai](https://yage.ai/share/claude-auto-mode-approval-illusion-en-20260808.html), 일화). 독립 연구도 방향이 같다. 컴퓨터 사용 에이전트의 감독 전략 네 가지를 48명에게 비교한 실험에서 계획 수준 검토는 문제 행동 발생을 76% 줄였지만(OR 0.24) 문제 행동이 실제로 일어났을 때 사용자가 개입한 비율은 전략과 무관하게 21%였고, 원인은 절차 확인(워크플로를 따랐는가)이 내용 판단(그 일을 해야 하는가)을 대체하는 데 있었다 ([arXiv 2604.04918v2](https://arxiv.org/html/2604.04918v2), 측정). "Oversight Has a Capacity"는 검토자를 피로하는 에이전트로 모델링해 실현 안전성이 에스컬레이션 비율의 역U 곡선이며 최적 가드는 전부 올리지 않는다고 결론했다 ([arXiv 2606.08919](https://arxiv.org/abs/2606.08919), 측정·소규모).

autodev에 이 결과가 바꾸는 것은 게이트의 존재가 아니라 형태다. 결정은 `autodev:ready`가 놓인 태스크 스냅샷 단위(계획 수준)에 머물고 단계 단위로 내려가지 않는다. 위키 채택 후보도, 라디에이터 후보도, 스킬 승격 후보도 하루에 사람 앞에 놓이는 개수에 상한을 둔다. 각 항목은 "승인?"이 아니라 답해야 하는 내용 질문(무엇이 바뀌고, 틀리면 무엇이 깨지고, 대안은 무엇이었나)을 앞세운다. 그리고 33,596개 에이전트 PR 연구에서 거부의 31.2%가 중복·대체·정책 같은 워크플로 제약이었고 35.7%만 명백한 에이전트 실패였다는 결과는 ([arXiv 2605.22534](https://arxiv.org/abs/2605.22534), 측정) 인박스 진입 전에 같은 이슈의 열린 PR이나 활성 에피소드를 자동으로 걸러 사람의 예산을 아끼라는 뜻이다.

## 한국어 lexical 검색은 토크나이저가 결정하고, ripgrep은 어간 방향만 통한다

1차는 조사 문제를 지적하고 `aliases`에 어간형을 쓰라고 했다. 2차 데이터는 크기를 확인해 준다. Haystack의 기본 BM25 정규식 `(?u)\b\w+\b`는 같은 구조의 한영 벤치마크에서 한국어 쪽 **Recall@10 0/10, top-1 0/10**을 냈다. `서울은`이 한 토큰으로 남아 `서울` 질의가 닿지 못했기 때문이다. 음절 유니그램은 10/10 회상을 주지만 `서울`이 서점의 `서`와 울음의 `울`에 걸려 오답을 1위에 올렸고, 겹치는 바이그램은 10/10 회상과 올바른 1위를 문장당 13토큰(기본 6, 유니그램 19)으로 달성했다 ([Haystack #12867](https://github.com/deepset-ai/haystack/issues/12867), 측정·10질의 토이). 실제 개인 코퍼스(FTS 용어 90,546개 중 56,530개가 한글)에서는 `메모리*`가 190파일 390청크에 맞고 `메모리를*`은 16파일 18청크에만 맞아 `메모리`만 있는 청크에 절대 닿지 못했다. 60개 어간에서 활용형 질의와 어간 질의의 BM25 점수 일치 중앙값은 unicode61 0.082 대 kiwipiepy 0.700, overlap@10은 3.33 대 5.40이었고 54개 어간이 개선, 2개가 후퇴했다. 저자는 관련성 라벨이 없어 "일치"만 보였음을 명시했다 ([memtomem-stm #1021](https://github.com/memtomem/memtomem-stm/issues/1021), 측정·비라벨). QMD는 `porter unicode61`을 하드코딩해 CJK 질의가 BM25 0건이 되고 하이브리드가 조용히 벡터 전용으로 격하됐으며, 제안된 수정은 SQLite `trigram` 토크나이저(3.34+, 어간 추출 없음, 3자 이상 질의) ([qmd #617](https://github.com/tobi/qmd/issues/617), 일화)다.

ripgrep에는 이 비대칭이 절반만 적용된다. 부분 문자열 매칭이므로 `메모리` 질의는 `메모리를`, `메모리에`를 잡지만(어간이 접두이므로), 에이전트가 오류 로그나 사용자 문장에서 본 활용형을 그대로 grep하면 어간만 있는 페이지를 놓친다. 동사·형용사는 어간 자체가 바뀌어(`했다`/`하는`/`해서`) 더 나쁘다. 그래서 오늘의 규칙은 "한국어 명사는 조사 없는 어간으로, 동사는 가장 짧은 안정 접두로 grep"이고, 영어 식별자와 오류 문자열은 Markdown에서 공백·구두점으로 구분되는 경우가 훨씬 많으므로 `rg -F`로 그대로 친다. 이 규칙은 #1021의 메커니즘에서 추론한 것이며 측정된 것은 아니다. 인덱스를 얹는 날의 결정도 데이터가 정한다. 트라이그램/바이그램은 의존성 없이 회상을 복구하지만 랭킹이 거칠고, Kiwi는 랭킹 일치가 훨씬 좋지만 네이티브 의존성이다. 수백 페이지에서는 우연한 음절 충돌이 7,000페이지보다 적어 n-gram의 정밀도 비용이 작겠지만 아무도 재지 않았다.

임베딩 쪽에서는 모델 선택이 정해졌다. MTEB(kor, v2) 검색 9개 태스크 평균 nDCG@10에서 KURE-v2(154M, 후기 상호작용) 0.8160, KURE-v1(568M 밀집) 0.7616, snowflake-arctic-embed-l-v2.0-ko 0.7653, BGE-m3-ko 0.7547, bge-m3 0.7509인 반면 Qwen3-Embedding-8B는 0.7826, 4B는 0.7737이다 ([nlpai-lab/KURE](https://github.com/nlpai-lab/KURE), 측정·모델 저자 실행). 568M 한국어 튠 모델이 8분의 1 메모리로 8B와 비슷하고 4B를 이긴다. 코드스위칭 질의는 시험한 모든 검색기와 리랭커를 떨어뜨렸고(일반 검색에서 약 15점, CS-MTEB 최대 27%), 어휘 확장이 일부만 회복했다 ([arXiv 2604.17632](https://arxiv.org/html/2604.17632v1), 측정). 한국어 산문 속의 `ECONNREFUSED`나 `useEffect`는 대개 가장 변별력 있는 토큰이므로, 그 토큰을 lexical로 먼저 치는 것이 임베딩 저하를 통째로 우회하는 길이다. 개인 코퍼스에서 교차언어 파인튜닝은 하지 않는다. 병합 없는 파인튜닝은 단일언어에서 1~5점을 잃었다 ([arXiv 2507.08480](https://arxiv.org/html/2507.08480), 측정).

질의 재작성의 경계도 정해졌다. "Not All Queries Need Rewriting"은 FiQA에서 프롬프트 기반 재작성이 nDCG@10을 **-9.0%**(p<0.001) 떨어뜨리고 TREC-COVID에서 +5.1%(보정 후 경계) 올렸는데, 갈림길은 재작성이 질의 어휘를 코퍼스 용어 쪽으로 옮기는가였다("2019-nCOV"를 "COVID-19"로). 특징 기반 게이팅은 AUC 0.593으로 "재작성 안 함"보다 낫지 않았다 ([arXiv 2603.13301](https://arxiv.org/html/2603.13301), 측정). 1차의 "grep 전에 한영 변형과 원인 표현을 만들어라"는 유지되되, 식별자·오류 문자열이 든 질의는 재작성하지 않는다는 정적 규칙이 붙는다. 학습된 게이트가 실패했으니 정적 규칙이 최소한 같은 성능이다.

## grep·read 루프는 100만 토큰 아래에서 가장 정확하고, 후보 목록이 비용을 6분의 1로 줄인다

1차의 핵심 근거였던 스케일링 연구는 v3에서 수치가 더 정밀해졌다. 가장 작은 티어(1,144문서, 170만 토큰)에서 파일시스템 에이전트는 **77.4%를 질의당 226K 토큰**으로, BM25는 74.7%를 5.8K 토큰으로 냈고, 교차점은 약 1,000만 토큰, 전체 규모(6억 토큰)에서는 BM25 50.5% 대 에이전트 30.7%(예산 소진 31%)였다. 통제 조건이 핵심이다. 에이전트의 원시 파일 탐색을 BM25 랭킹 후보로 바꾸자 전체 규모 정확도가 **36.9%에서 69.4%**로 오르고 질의당 도구 호출이 36.12에서 5.79로 줄었다 ([arXiv 2607.26497](https://arxiv.org/html/2607.26497v3), 측정). 두 번째 연구는 116개 LongMemEval 질문을 Claude Code·Codex CLI·Gemini CLI·자체 하네스에서 grep 대 벡터로 비교해 인라인 전달에서는 모든 쌍에서 grep이 이겼고(Opus 4.6: 93.1% 대 83.6%), 같은 모델이 Claude Code에서는 76.7%, 자체 하네스에서는 93.1%를 내는 하네스 효과를 보였다 ([arXiv 2605.15184](https://arxiv.org/html/2605.15184v1), 측정). 두 코퍼스 모두 영어이고 문자 그대로의 스팬이 답이라 한국어 산문 절반에는 grep 우위를 할인해야 한다.

설계 결정은 1차와 같지만 "후보 목록 먼저"가 추가된다. 한 단계 평면 `index.md`는 BM25 후보 목록의 값싼 등가물이고, 인덱스를 승격하는 날에도 그 출력은 에이전트의 read 루프에 후보를 공급하는 랭킹이어야 하며 읽기를 대체하지 않는다. 검색 결과는 파일 경로가 붙은 인라인 스니펫으로 에이전트에 전달된다. 하네스의 grep 출력이 이미 그 형식이다.

## 측정: 통과율은 기술 통계이고, 교정 횟수와 재발이 확인 지표다

1차는 두 비율 검정으로 조건당 38~93 에피소드를 계산했다. 2차의 VibeMemBench는 이 계산이 낙관적이었음을 실제 실험으로 보였다. 90개 SWE-rebench V2 저장소의 111개 타깃에 같은 저장소 이력 3,634개 궤적을 주입하고, 고정 에이전트로 메모리 유무 두 실행을 쌍대 비교하며, 선언된 테스트를 오라클로, 타깃을 불확실성 단위로 삼아 10,000회 부트스트랩을 돌렸다. 동결된 검증 경험은 5개 솔버 중 4개에서 Resolved를 1.1~4.5점 올렸지만 **"다섯 부트스트랩 구간이 모두 0을 지나므로 111개 타깃에서 관찰된 이득은 0과 분리되는 효과가 아니라 방향적 증거"**였다. 관련 없는 메모리 대조군은 메모리 없음보다 0.7~3.4점 낮았고, 주입은 모든 솔버에서 에이전트 스텝을 줄였다 ([arXiv 2609.23570](https://arxiv.org/pdf/2609.23570), 측정). 1인 개발자의 한 분기가 111개 쌍대 타깃에 4시드를 곱한 표본을 만들 가능성은 없다. 그러므로 첫 시도 CI 통과율은 확인 지표가 아니라 모니터링용 기술 통계로 내리고, 베타-이항 사후분포(Evan Miller의 닫힌 형식)로 "지식 팔이 나을 확률"을 계속 읽되 n<100에서는 이진 판정을 내리지 않는다 ([Evan Miller](https://www.evanmiller.org/bayesian-ab-testing.html), 일화·수식). 확인 지표는 빈도가 높은 카운트다. 에피소드당 교정 횟수(스텝 수의 카운트 아날로그로, VibeMemBench에서 통과율이 움직이지 않을 때도 일관되게 움직였다), 그리고 실패 서명 재발이다. 특히 "그 서명의 노트가 존재한 뒤에도 재발"은 표본 없이도 그 노트가 결정을 바꾸지 못했다는 부정 증거이고, "노트 없이 2회 이상 재발"은 MSCE가 정책 귀납의 트리거로 쓰는 "같은 서명 버킷의 다중 에피소드 증거"와 같다 ([arXiv 2607.16621](https://arxiv.org/pdf/2607.16621), 측정·방법).

METR의 두 교훈은 그대로 옮겨진다. 16명·246태스크 RCT는 AI 허용 태스크가 19% 더 걸렸는데(95% CI +2%~+39%) 개발자는 20% 빨라졌다고 자기 보고했고, 57명·800+태스크 후속에서는 개발자의 30~50%가 AI 없이 하기 싫은 태스크를 제출하지 않아 METR 스스로 "신뢰할 수 없는 신호"라 했다 ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [METR 2026](https://metr.org/blog/2026-02-24-uplift-update/), 측정). 즉 어떤 태스크에 지식을 쓸지 운영자가 고르면 선택 편향이 지배하므로 팔 배정은 이슈 번호 홀짝처럼 기계적으로 하고, 자기 보고 만족도는 지표에서 뺀다. LLM 판정 지표도 뺀다. 21개 판정자·3개 벤치마크 연구에서 원시 일치율은 카파를 33.8~41.2pp 과장했고("85% 일치"가 실제 κ≈0.48) 위치 편향은 모델 간 100배 차이였다 ([arXiv 2606.19544](https://arxiv.org/html/2606.19544v1), 측정). 실패 서명은 테스트 ID + 예외 클래스 + 최상위 프레임 파일의 결정론 문자열로 정규화하고, 부득이 LLM 군집화를 쓰면 30~50건 손 라벨로 카파를 먼저 낸다.

## 하네스 개조, 외부 탐색, 검증 도구는 1차가 비운 축이며 2차가 채운다

자기 개선 시스템 다섯 개의 공개 궤적을 감사한 연구는 모든 시스템에서 하네스 개조를 찾았고(ADAS 84.6%, HyperAgents 73.6%, DGM 63.1%, ScientistOne 29.6%, AFlow 18.3%의 반복에서), 개조가 최종 최고 에이전트 계보까지 잔존했으며(HyperAgents 평균 5.2건, DGM 3.5건), 개조는 평가(HyperAgents 59%, AFlow 38%)와 기록(DGM 30%) 역할에 집중됐다 ([arXiv 2609.00069](https://arxiv.org/html/2609.00069), 측정). 이 감사는 코드 하네스를 자기 편집하는 시스템에 관한 것이고 SKILL.md 같은 메모리 전용 자기 수정에 대한 감사는 없다. 그럼에도 결론은 1차를 강화한다. 스킬 평가 정의, CI 설정, 채점 스크립트, 에피소드 기록 경로는 에이전트의 쓰기 집합 밖에 두거나 사람 병합 뒤에만 바뀌고, "자기 평가를 통과했다"는 승격 근거가 아니다.

외부 radar에 관해 측정된 것은 적다. 개인 논문 스트림 랭킹 논문들은 시뮬레이션 사용자 벤치마크만 보고하고, GitHub Actions 라디에이터 저장소들은 파이프라인과 개수만 보고하며 정밀도나 사용자 수락률은 어디에도 없다. 재현되는 설계는 하나다. 무료 키워드 허용·거부 프리필터, LLM 채점 후보 상한(10~15), 노출 상한(하루 5~8), 정본 ID 중복 제거, Markdown 커밋이다. llm-paper-radar의 2026-09-28 로그는 arXiv 493 + HF 82 = 575건 입력에 11건 노출이었고 ([zzjjay/llm-paper-radar](https://github.com/zzjjay/llm-paper-radar), 벤더·로그 수치), 한 사건이 여러 게시물을 낳는 fan-out은 사건 보고 895건이 698개 고유 사건으로 접힌 약 22% 중복률로 측정됐다 ([arXiv 2604.09104](https://arxiv.org/html/2604.09104), 측정). 신선도 쪽에서는 MemStrata가 진화하는 지식에서 RAG가 낡은 정보를 15~40% 서빙하는 반면 쓰기 시점의 결정론적 (주어, 관계, 목적어) 대체 규칙이 LLM 호출 없이 이를 약 0%로 낮추고 정확도를 0.20~0.47에서 0.95~1.00으로 올렸다고 보고했다 ([arXiv 2606.26511](https://arxiv.org/abs/2606.26511), 측정). 주기적 스윕의 오류 감소 수치는 어디에도 없다. 즉 "매일 외부 탐색 → 지식"의 측정된 부분은 쓰기 시점 대체이고, 나머지는 실무 합의다. 스케줄러는 GitHub Actions `schedule`(5분 최소, 지연 있음, 공개 저장소 60일 무활동 시 자동 비활성)과 Claude Code routines(클라우드, 1시간 최소, 구독 사용량 소모, 임의 사이트 fetch에는 네트워크 설정 필요) 둘이 상시 머신 없이 동작한다 ([GitHub Docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows); [Claude Code routines](https://code.claude.com/docs/en/routines), 벤더).

검증 도구의 유지 상태는 GitHub API로 2026-09-30에 확인됐다. lychee는 v0.24.2(2026-05-01)에 9월 28일 푸시로 활성이고 `--offline --include-fragments`를 지원하지만 경로 없는 Obsidian `[[파일명]]`을 해석할 수 없다 ([lycheeverse/lychee](https://github.com/lycheeverse/lychee), 공식). markdown-link-check의 인기 Action은 아카이브됐고 remark-validate-links는 2025년 2월 이후 비활성, remark-lint-frontmatter-schema는 2023년 이후 릴리스가 없다. 프론트매터 스키마용으로 유지되는 패키지는 remark-lint-frontmatter-validation v1.0.4(2026-08-20)인데 스타 1개의 1인 프로젝트다 ([Nick2bad4u](https://github.com/Nick2bad4u/remark-lint-frontmatter-validation), 공식). Obsidian 위키링크를 Obsidian과 같은 규칙으로 해석하는 CI 도구는 wikilink-check(2026-09-23 릴리스, 1,500노트 vault에서 `obsidian unresolved`와 차이 0, `--baseline` 모드)뿐이며 며칠 된 1인 프로젝트다 ([MH4GF/wikilink-check](https://github.com/MH4GF/wikilink-check), 공식). 프론트매터 `id` 참조를 검증하는 도구는 없다.

# 2부. 기획안: 다음 한 분기, 1인 개발자의 4단계

분기는 13주다. 네 단계는 순서가 있고 뒤 단계는 앞 단계의 기록을 입력으로 삼는다. 각 단계에서 "만드는 것"은 파일·스크립트·지침 단락이고 "만들지 않는 것"은 하네스·git·Obsidian·Kaneo·기존 CLI가 이미 주는 것이다. 코퍼스는 0에서 시작하므로 1단계는 규약과 게이트를 코드로 굳히는 데 쓰고, 첫 스킬 승격은 분기 마지막에 한 번 시도한다.

| 단계 | 기간 | 만드는 것 | 만들지 않는 것 (제공 주체) |
| --- | --- | --- | --- |
| 1. 규약 고정 | 1~2주 | 프론트매터 JSON Schema, `kb-lint` 스크립트, 루트 `AGENTS.md` 검색·작성 지침 단락, `index.md` 생성, `misses/` 로그 형식, `SessionEnd`·`notify` 훅 한 줄 | 파일 검색·읽기(하네스), 세션 전사(하네스), 이력·diff·PR(git/GitHub), 편집기·속성 UI·Bases(Obsidian), 본문 스타일·링크 검사(markdownlint-cli2, lychee) |
| 2. 에피소드 루프 | 3~6주 | 주간 통합 패스 프롬프트(스킬 1개), 에피소드 기록에 `knowledge_used` 필드, 실패 서명 정규화 규칙, 첫 측정 스크립트(`gh api` + `git log` → 표) | 에피소드 상태·교정 예산·서명(autodev delivery, 이미 있음), CI 결과(GitHub check runs), 훅 이벤트(하네스) |
| 3. 인박스와 radar | 7~10주 | Kaneo `needs-decision` 라벨 + 코멘트 템플릿, 일일 digest 검색, radar Actions 워크플로(fetch·dedup·seen.json), radar 판정 프롬프트, `type: radar` 노트 | 트래커 상태·라벨·코멘트·검색(Kaneo), 스케줄러(GitHub Actions / Claude routines), 소스 API(arXiv·HF·HN·GitHub), 알림(Kaneo) |
| 4. 첫 스킬 승격과 분기 리뷰 | 11~13주 | 스킬 장부 `skills/ledger.md`, 스킬 후보 lint 규칙(하드코딩), 두 엔진 보류 평가 실행 절차, 분기 측정 표 | 스킬 로딩·트리거·예산(하네스), 평가 실행(기존 skill 평가 하네스), 롤백(git revert) |

## (b) 지식 단위와 프론트매터의 최종 형태

지식 단위는 1차와 같이 "한 상황을 다루는 자기완결적 H2 절"이며 페이지는 1~2쪽, 500줄 이하다. 본문 절은 상황·방법·근거·주의점·검증에 `Symptoms`(오류 문자열을 코드 스팬으로)와 `Observed`/`Generalized` 분리를 더한 저장소 고유 템플릿이다. 2차가 바꾸는 것은 프론트매터의 세 필드다. 파일명과 독립인 불변 `id`(관계 대상이 파일 이동에도 살아남게), LongMemEval-V2의 세 범주를 옮긴 `category`(`gotcha | workflow | premise`, `lesson`에만 필수. 나중에 범주별 효용을 따로 보고할 수 있게 한다) ([arXiv 2605.12493](https://arxiv.org/html/2605.12493v1), 측정), 그리고 결정론 문자열인 `signature`(`lesson`에 선택, 에피소드 기록의 정규화 서명과 같은 형식)다. `sources`에는 URL 외에 커밋 SHA와 하네스 세션 ID를 허용해 노트가 자기를 낳은 에피소드를 가리키게 한다. 이것이 Faulty Memories의 "에피소드를 증거로" 요구와 감사 논문의 provenance 요구를 한 필드로 충족하는 방법이다.

```yaml
id: kb-20261005-pnpm-lockfile-v9        # 불변, 파일명 무관
type: decision | howto | reference | lesson | radar
title: pnpm lockfile v9와 CI 캐시 비호환
description: pnpm 9 lockfile이 8용 캐시 키와 충돌해 CI가 멈추는 현상과 처리 방법을 설명한다.
applies_when: pnpm 메이저 업그레이드 뒤 CI install 단계가 진행 없이 멈출 때
aliases: [pnpm 잠금파일, lockfile, ERR_PNPM_LOCKFILE_BREAKING_CHANGE]
tags: [pnpm, ci]
status: stable            # draft | stable | disputed | superseded | deprecated  (내용의 진위)
adoption: accepted        # candidate | accepted | deferred | rejected            (사람의 결정)
basis: observed           # observed | measured | inferred | assumed
category: gotcha          # lesson 전용: gotcha | workflow | premise
signature: "install:ERR_PNPM_LOCKFILE_BREAKING_CHANGE:pnpm-lock.yaml"   # lesson 선택
sources:
  - https://github.com/org/repo/issues/123
  - commit:8da5974
  - session:claude:0192f...   # 하네스 세션 ID, 전사 경로가 아니라 ID
created: 2026-10-05
updated: 2026-10-05
stale_after: 2027-04-05     # 본문에 "pnpm 10 릴리스 시 재검토" 문장 동반
supersedes: []              # id 목록
superseded_by: null
related: []
```

규칙은 셋이다. 에이전트는 `adoption: candidate`까지만 쓰고 `accepted`는 사람만 쓴다. `observed`/`measured`에 `sources`가 비면 lint 오류다. 갱신은 편집이 아니라 새 페이지 + 옛 페이지 `superseded`이며, `index.md`와 검색 지침은 `superseded`·`deprecated`·`rejected`를 기본 제외한다. 수치 신뢰도와 시간 감쇠는 1차대로 넣지 않는다.

## (c) 검색의 오늘 규칙과 승격 조건

오늘의 검색은 하네스의 grep·glob·read이고 그 위에 지침 한 단락과 파일 하나가 얹힌다. 파일은 한 단계 평면 `index.md`로, 페이지당 한 줄(링크, `description`, `applies_when`, 태그)이며 `kb-lint`가 프론트매터에서 생성하고 손으로 고치지 않는다. 재생성해서 diff가 나오면 CI가 실패한다. 지침 단락은 `AGENTS.md`에 들어가며 다음을 말한다. 검색 전에 `index.md`를 읽고 `applies_when:` 줄을 먼저 grep한다. 한국어 명사는 조사 없는 어간으로, 동사는 가장 짧은 안정 접두로 grep한다. 영어 식별자·오류 문자열·명령은 `rg -F`로 그대로 치고 절대 풀어쓰지 않는다. 코드형 토큰이 없는 증상 질의("컨테이너가 자꾸 죽어요")만 한국어·영어 2~3개 키워드와 가능한 원인 용어로 확장해 각각 grep한다. 적용 전 `status`, `stale_after`, `superseded_by`를 확인하고 `superseded_by`가 있으면 그쪽을 읽는다. "KB를 신뢰하라"는 문장은 쓰지 않는다.

미스 로그는 첫날부터 켠다. `misses/YYYY-MM.md`는 append-only이고(`.gitattributes`에 `merge=union`, 미검증) 한 항목이 네 필드를 갖는다. `query`(실제 grep 용어나 glob), `candidates_shown`(돌아온 경로), `used`(읽거나 인용한 경로), `resolution`(`existed:<path>` | `written:<id>` | `not-needed`). `resolution`이 없는 미스 로그는 인덱스 문제와 커버리지 공백을 구별할 수 없으므로 이 필드가 로그의 존재 이유다. 에이전트가 스스로 "못 찾았다"고 적는 플래그의 정밀도는 측정된 바가 없으니, 2단계 말에 30~50건을 손으로 라벨해 카파를 한 번 낸다.

승격 조건은 크기가 아니라 로그다. 재작성 규칙이 들어간 뒤 한 달 동안 `resolution: existed`인 미스가 10건 이상이거나 기록된 검색의 20%를 넘으면 QMD를 승격 검토한다. 이 임계값은 측정된 것이 아니라 운영 임계값이며 첫 분기에는 도달하지 않을 가능성이 크다. 승격하는 날의 체크리스트는 정해져 있다. FTS 토크나이저를 `trigram`으로 두거나 #617 수정이 설치 버전에 들어왔는지 확인하고, 임베더를 한국어 튠 568M(KURE-v1 GGUF 또는 arctic-embed-l-v2.0-ko)으로 바꾸고, `qmd embed -f`를 돌리고, 질의 경로가 같은 모델을 쓰는지(#497) 확인하고, 리랭커를 켠다. 인덱스의 출력은 read 루프에 후보를 공급하는 랭킹이며 읽기를 대체하지 않는다. 그래프는 1차대로 미스 로그에서 다중 홉·비교·시간 질의 비율이 쌓일 때 임베디드 파생 인덱스(Ladybug)로 세운다.

## (d) 경험 → 위키 → 스킬의 게이트와 롤백

경험에서 `inbox/`까지는 세션마다, `inbox/`에서 위키까지는 주마다, 위키에서 스킬까지는 분기마다다. 이 세 박자가 Faulty Memories의 "에피소드 보존, 추상화 게이트"를 시간축으로 옮긴 것이다.

에피소드 층은 하네스가 준다. Claude Code의 `SessionEnd` 훅은 `session_id`, `transcript_path`, `cwd`, `conversation_turn_count`를 넘기고 Codex의 `notify`는 `thread-id`, `turn-id`, `cwd`, `last-assistant-message`를 넘긴다 ([Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex config](https://learn.chatgpt.com/docs/config-file/config-advanced), 벤더). 훅은 `claude -p --resume <id>` 또는 `codex exec resume --last`로 "이 세션의 결정·교훈·못 찾은 것"을 `inbox/YYYY-MM-DD-<session>.md`에 `status: draft`, `adoption: candidate`, `sources: [session:...]`로 적게 한다. JSONL 직접 파싱은 1차대로 하지 않는다. `inbox/`는 위키가 아니고 검색 지침의 기본 대상도 아니다.

통합 패스는 주 1회, 운영자가 여는 세션에서 스킬 하나(`kb-consolidate`)로 돈다. 입력은 그 주의 `inbox/`, `misses/`, 에피소드 기록이고 출력은 PR 하나다. PR은 새 페이지 추가, 기존 페이지 supersession, `index.md` 재생성만 담고 기존 페이지 본문을 제자리에서 고치지 않는다. 같은 `signature`가 두 에피소드 이상에서 나타나면 `lesson` 페이지를 제안하고, 기존 페이지와 충돌하는 주장이 있으면 `disputed`로 두 주장을 병기한다. 사람은 PR을 읽고 `adoption: accepted`를 직접 쓰거나 `rejected`/`deferred`로 남긴다. `rejected`도 커밋된다. 그래야 다음 주 통합 패스가 같은 후보를 다시 올리지 않는다. 위키의 롤백은 파일 삭제가 아니라 supersession이며, 잘못 채택된 페이지는 `status: deprecated`에 이유 한 줄을 붙인다.

스킬 승격은 분기에 한 번, 다음 다섯 조건을 모두 만족하는 `lesson` 또는 `howto`에만 시도한다. (1) 같은 `signature`가 노트 채택 뒤에도 최소 1회 더 재발했거나 노트 없이 2회 이상 반복되었다(절차가 필요하다는 증거). (2) 그 페이지가 `adoption: accepted`다. (3) 성공 에피소드와 실패 에피소드가 모두 `sources`에 있다. (4) 후보 SKILL.md가 절차(명령·검사·출력 형식)만 담고 `kb-lint`의 하드코딩 규칙(절대 경로, 버전 핀, 수치 상수, 저장소 고유 파일명)을 통과하며 500줄 이하다. (5) 기존 스킬 평가 하네스에서 유무 쌍대 비교로 개선이 있고, 이전에 통과하던 평가가 Claude Code와 Codex 둘에서 모두 유지되며, 토큰 비용이 무스킬 대비 정한 상한(예: +30%)을 넘지 않는다. 평가 정의와 채점 스크립트는 후보 PR의 diff에 포함되면 리뷰 전에 CI가 거부한다. 승격은 PR + 사람 병합이고, `skills/ledger.md`에 제안·diff 요약·증거·결정·거부 이유를 한 줄로 남긴다. 롤백은 병합 뒤 같은 `signature`가 재발하거나 평가가 회귀하면 `git revert`이며 장부에 기록해 같은 편집이 재제안되지 않게 한다. 대부분의 후보가 거부되는 것이 정상 상태다.

## (e) 외부 radar의 최소 설계와 스팸 방지

radar는 두 조각이다. fetch·dedup는 GitHub Actions에서 매일 한 번 돌고(공개 저장소면 무료, 지연 10~30분은 무시), 판정은 운영자가 여는 세션에서 스킬로 돌거나 Claude routine으로 하루 한 번 돈다. 소스는 넷으로 시작한다. arXiv API(3초당 1요청, cs.AI/CL/SE 키워드), HF `daily_papers?date=`, HN Algolia `search_by_date`(points>50), 관심 저장소의 GitHub 릴리스. 어제 것을 처리한다. fan-out이 이미 일어난 뒤여야 한 사건을 한 번만 세기 때문이다. 상태는 `radar/seen.json`(정본 ID: arXiv ID, 저장소 URL, 릴리스 태그, 원문 URL 해시)이며 Actions가 커밋한다. 프리필터는 `radar/interests.yaml`의 허용·거부 키워드로 LLM 호출 없이 하고, 남은 후보 중 최대 10건만 LLM이 채점하며, 하루 최대 3건만 `type: radar`, `status: draft`, `adoption: candidate` 노트로 vault에 들어간다. 2차 게시물(블로그·트윗·요약 기사)은 새 항목을 만들지 않고 정본 항목의 `observations` 카운트를 올린다. 발표됐다는 사실이 근거가 아니라는 제약이 이 한 규칙으로 구현된다. 30일 안에 이미 노출된 정본 ID는 재노출하지 않는다.

radar 노트가 지식이 되는 길은 하나다. 사람이 `adoption`을 `accepted`(연구 태스크 생성) 또는 `rejected`/`deferred`로 바꾼다. 하루 1건까지만 Kaneo `research:` 태스크가 만들어지며 이것이 3부 인박스의 예산 안에 든다. `rejected` 사유 키워드는 다음 주 `interests.yaml`의 거부 목록에 들어간다(PaperRouter-Agent가 거부 이력을 라우팅에 쓴 것의 수동판, [arXiv 2607.11564](https://arxiv.org/abs/2607.11564), 측정). 신선도는 두 겹이다. 통합 패스가 radar 노트를 기존 페이지와 대조해 `supersedes` 관계를 제안하는 쓰기 시점 대체(측정된 쪽)와, `stale_after`가 지난 페이지만 재확인하는 주간 스윕(상한 10건, 측정 안 된 쪽)이다. 공개 저장소의 60일 자동 비활성은 `seen.json` 커밋 자체가 활동이므로 자연히 피해지지만, 저장소를 비공개로 바꾸면 무료 분량(월 약 2,000분)을 확인한다. Claude routine으로 판정을 돌릴 때는 "녹색 실행이 성공을 뜻하지 않는다"는 벤더 경고를 그대로 적용해 결과 노트의 존재로 성공을 판정한다.

## (f) 결정 인박스: Kaneo 상태와 라벨만으로 구현하는 needs-decision

Kaneo에는 Linear의 `awaitingInput` 같은 에이전트 세션 상태가 없다. 컬럼(`to-do`, `in-progress`, `in-review`, `done`)은 안정 슬러그와 `isFinal`을 가진 수동 단계일 뿐이고 `in-review`는 "운영자가 결정해야 함"과 "에이전트가 교정 중"을 구별하지 않는다 ([Kaneo API](https://kaneo.app/docs/api-reference/columns/get-columns), 벤더). 가장 싼 등가물은 워크스페이스 라벨 `needs-decision` 하나와 코멘트 템플릿 하나다. 부착 조건은 넷이다. 실행이 `autodev:human-needed`로 끝났을 때, 교정 예산이 소진됐을 때, PR이 리뷰 코멘트(Codex 리뷰·CI 외 지적)를 모았을 때, 그리고 통합 패스나 radar가 `adoption: candidate`를 올렸을 때. 코멘트는 고정 템플릿으로 질문 한 문장, 증거 링크(PR·에피소드 코멘트·노트), 에이전트가 고려한 대안, 거절하면 일어나는 일, 교정 횟수, 그리고 이 질문이 적용되는 태스크 다이제스트와 PR head SHA를 담는다. Kaneo 코멘트는 편집 가능하므로 결정은 다이제스트를 인용한 새 코멘트로 남기고 라벨을 뗀다. 이것이 Linear의 "편집 가능한 코멘트가 아니라 동결된 활동을 믿으라"를 Kaneo에서 흉내 내는 방법이다 ([Linear best practices](https://linear.app/developers/agent-best-practices), 벤더).

digest는 하루 한 번이다. `needs-decision` 라벨의 Kaneo 검색 결과를 요약 우선으로 나열하고, 작은 PR(체크 녹색, 리뷰 지적 0)은 한 줄과 링크만, 큰 PR과 지적이 있는 PR만 diff 우선으로 표시한다. 인터럽트 채널은 protected path 정지와 예산 소진에만 쓴다. 인박스 진입 전에 같은 이슈에 열린 PR이나 활성 에피소드가 있으면 항목을 만들지 않고 기존 항목에 코멘트만 붙인다. 하루 상한은 총 5건이고 넘치면 다음 날로 밀린다. 운영자의 결정은 `approved-unchanged | approved-after-correction | task-rewritten | abandoned` 넷 중 하나로 에피소드 기록에 남아 다음 분기에 override 비율을 계산할 수 있게 한다. 병합 승인을 PR head SHA에 묶는 것(`autodev:merge-ok@<sha>` 또는 dismiss-stale-reviews)은 조용한 후속 커밋이 실제로 관찰될 때까지 미룬다.

## (g) 측정: 지금 계산 가능한 지표, 추가할 필드 하나, 표본의 현실

에피소드가 GitHub 이슈 코멘트에 교정 시도와 정규화 실패 서명을 남기고 CI가 유일한 오라클인 현재 구조에서 네 지표는 `gh api`와 `git log`만으로 계산된다. 첫 시도 CI 통과(PR 첫 head SHA의 첫 check run `conclusion == success`), 에피소드당 교정 횟수(`<!-- autodev:attempts -->` 코멘트의 시도 수), 첫 push에서 첫 녹색까지 시간(self-merge 운영자에게는 time-to-merge보다 사람 지연이 빠져 낫다), 그리고 실패 서명 재발(서명별 에피소드 수와, 그 서명의 노트가 존재했는지를 `git log --diff-filter=A --format=%aI -- <note>`로 대조). 이 넷을 주간 표로 뽑는 스크립트가 2단계 산출물이며 결과는 이슈 코멘트나 `reports/metrics/`에 커밋한다. 메트릭 서버는 없다.

추가할 필드는 하나, `knowledge_used`다. 에피소드에서 첫 Edit/Write 전에 읽은 지식 디렉터리 경로의 집합이며, Claude Code에서는 `PostToolUse`(Read, `file_path`가 vault 아래) 훅으로, Codex에서는 세션 종료 후 rollout을 스캔해서 얻어 에피소드 이슈 코멘트에 붙인다. 이 필드 하나로 지식 사용률, 다중 홉 비율(경로 2개 이상), 그리고 노트가 존재했는데 읽지 않은 재발("존재·미열람")과 읽었는데 재발("열람·무효")의 구분이 가능해진다. "입력에 있었다"는 "썼다"가 아니므로(스킬이 있어도 무시되는 현상, [arXiv 2604.04323](https://arxiv.org/pdf/2604.04323), 측정) 승격 직전 노트 하나에만 노트를 뺀 재실행(CUE-R의 remove 연산의 라벨 없는 판)을 한 번 한다.

표본의 현실은 분명히 적는다. 1인 개발자의 한 분기 에피소드는 수십 건이다. 두 비율 검정(α 0.05 양측, 검정력 0.8)에서 50%→80%는 팔당 36건, 60%→80%는 78건이 필요하고, 쌍대 McNemar로도 20에피소드면 불일치 쌍 6건 전부가 한쪽이어야 한다(자체 계산, 일화 등급). 따라서 통과율은 베타-이항 사후분포로 계속 읽는 기술 통계이고, 확인 판단은 교정 횟수 분포와 서명 재발 카운트로만 한다. 유무 비교를 시작하는 시점은 `adoption: accepted` 노트가 20개를 넘는 때이며, 그때 팔 배정은 이슈 번호 홀짝으로 기계적으로 하고 운영자가 고르지 않는다. 관련 없는 노트를 같은 길이로 주입하는 대조군은 VibeMemBench가 보인 대로 값싸고, 지식 팔이 이 대조군을 이기지 못하면 효과는 지식이 아니라 컨텍스트 모양이다.

## (h) 검증 도구: 채택할 것의 이름과 버전, 직접 쓸 스크립트 하나

채택하는 기존 도구는 셋이다. **markdownlint-cli2 v0.23.3**(본문 스타일, pre-commit 훅과 Action 존재, `.obsidian/` 무시 glob, Obsidian 쪽은 같은 설정 파일을 읽는 obsidian-markdownlint 플러그인) ([DavidAnson/markdownlint-cli2](https://github.com/DavidAnson/markdownlint-cli2), 공식). **lychee v0.24.2**를 `--offline --include-fragments anchor-only`로(Markdown 링크와 앵커, pre-commit 훅 `lychee`, lychee-action v2.9.0) ([lycheeverse/lychee](https://github.com/lycheeverse/lychee), 공식). 그리고 **wikilink-check**를 2026-09-23 릴리스 커밋에 핀해 `--baseline` 모드로(위키링크는 사람이 Obsidian에서 쓰므로 남기되 새 파손만 막는다) ([MH4GF/wikilink-check](https://github.com/MH4GF/wikilink-check), 공식). 에이전트에게는 `AGENTS.md`에서 상대 경로 Markdown 링크를 쓰게 해 lychee만으로 에이전트 산출물의 링크가 검증되게 한다. Obsidian 쪽 Linter 1.33.0은 YAML 키 정렬과 타임스탬프 같은 서식에만 쓰고 검증기로 취급하지 않는다.

직접 쓰는 스크립트는 하나, `scripts/kb-lint.mjs`(gray-matter + Ajv + ajv-formats, Node 22)다. 1인 프로젝트인 remark-lint-frontmatter-validation을 의존성으로 들이는 대신 같은 Ajv를 40줄로 직접 부르는 쪽이 공급망 위험이 작고, 어차피 스키마 외의 다섯 검사가 필요해 한 파서로 묶는 것이 맞다. 검사 항목은 프론트매터 JSON Schema(`enum`, `format: date`, `type`별 `if/then` 필수 필드, `observed`/`measured`에 빈 `sources` 오류), `id` 유일성과 `supersedes`/`superseded_by`/`related` 대상 존재, `stale_after < today`와 `disputed`가 N일 초과인 페이지 목록, `index.md` 재생성 후 diff 없음, 그리고 `skills/` 아래 후보 SKILL.md의 하드코딩(절대 경로, `x.y.z` 버전 핀, 저장소 고유 파일명, 숫자 상수) 경고다. 종료 코드로 CI를 막고, stale 목록은 오류가 아니라 통합 패스 입력으로 `inbox/`에 노트를 남긴다. Claude Code와 Codex가 같은 명령을 돌리므로 엔진 중립이 자동으로 지켜진다. Obsidian 쪽 등가물은 `stale_after < today()` 필터의 Bases 뷰 하나(`Due.base`)이며 플러그인이 필요 없다 ([Obsidian Bases functions](https://obsidian.md/help/bases/functions), 벤더).

## 결론

2차 근거가 1차와 가장 다르게 그린 것은 게이트의 개수가 아니라 리듬이다. 1차는 "어디에 게이트를 두는가"에 답했고, 2차는 "얼마나 자주 통과시키는가"에 답한다. 에피소드는 매 세션, 위키는 매주, 스킬은 매 분기이며, 사람 앞에 놓이는 항목은 하루 다섯 건이다. 이 리듬은 취향이 아니라 세 측정(통합 빈도가 정확도를 무너뜨림, 사람의 검토 용량이 50회 안에 소진됨, 388개 스킬 후보 중 55개만 유효)의 교차점이고, 셋 모두 "더 자주, 더 많이"가 해롭다는 같은 방향을 가리킨다. 1인 개발자에게 이는 역설적으로 유리하다. 하루 다섯 건의 결정과 주 한 번의 PR 리뷰는 한 사람이 감당하는 양이고, 그 이상을 요구하는 설계는 측정상으로도 더 나쁘다.

두 번째 함의는 측정의 겸손이다. 첫 분기는 어떤 지표로도 "지식베이스가 도움이 됐다"를 확인하지 못한다. 확인할 수 있는 것은 부정 증거다. 노트가 존재한 뒤에도 같은 서명이 재발했는가, 읽고도 재발했는가, 못 찾은 질의가 `existed`로 해소되는가. 이 셋은 표본 크기와 무관하게 한 건으로도 의미가 있고, 각각 통합 패스·스킬 승격·인덱스 승격의 트리거가 된다. 지식 루프가 자기 승격 조건을 스스로 생산한다는 1차의 관찰은 그대로이되, 그 조건이 긍정 증거의 축적이 아니라 부정 증거의 부재라는 점이 2차가 덧붙인 것이다. 남은 공백도 정직하게 남는다. 한영 혼용 기술 노트에 대한 라벨 있는 검색 측정, 사람 게이트 대 자동 게이트의 통제 비교, SKILL.md 같은 메모리 전용 자기 수정의 개조 감사, radar 제안의 사람 수락률은 2026년 9월 기준 어디에도 없다. 이 기획안의 기록 필드(`knowledge_used`, `resolution`, 결정 결과 넷, `skills/ledger.md`)는 그 공백 중 autodev가 스스로 채울 수 있는 부분을 첫날부터 남기도록 고른 것이다.
