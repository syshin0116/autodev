# 개발 지식 구현 설계

상태: 설계 초안 · 작성일: 2026-09-10

[제품 기획](knowledge-product-plan.md)의 KNOW-01부터 KNOW-08까지를 저장·조회·갱신 계약과 구현 단위로 구체화한다. 결정 원본은 Kaneo AUT-1·AUT-2·AUT-3이며, 이 문서 작성은 ADR 승인이나 코드 구현 착수를 뜻하지 않는다. [기존 구현 제안](40-llm-wiki.md)의 위키 유지관리 원칙을 재사용하고 검색 카드·자산·코드 참조를 추가한다.

## 현재 구현에서 출발할 지점

| 확인한 대상 | 현재 동작 | 변경 방향 |
| --- | --- | --- |
| `SKILL.md` | 계획·실행·학습 가이드로 분기 | 지식 조회·수집·유지보수 요청을 프로젝트 계획 없이 라우팅 |
| `references/learning.md` | 프로젝트 근거에서 pending 후보 작성 | 기존 후보 형식을 읽고 지식 통합·검토 흐름으로 연결 |
| `src/lib.rs` | 계획 revision, Knowledge 출처·대상·권한 검증 | 실행 승인 검증을 유지. 지식 읽기가 전체 프로젝트 승인을 요구하지 않도록 분리 |
| `Cargo.toml` | YAML·JSON 파싱과 SHA 해시 의존성 | 결정론적 파일 검사가 필요하면 기존 의존성 활용 |
| `dev-knowledge/index.md`, `templates/github-issues/` | Markdown 설명과 실제 템플릿, `status: stable`, 출처·검증 메타데이터 | 경로와 자산을 유지하며 부족한 식별·채택·검증 범위만 추가 |

지식 저장소의 안내는 공개 상태라고 적고 있다. 실제 원격 공개 여부와 쓰기 대상은 수집 전에 확인한다. 이번 설계에서는 해당 저장소에 쓰지 않았다. 현재 PATH에서 `qmd`와 `neo4j` 실행 파일은 찾지 못했다. 두 도구는 설치 대상이 아니라 승격 조건(기획 6절)이 충족될 때의 후보다.

## 1. 실행 구성

Agent Host가 수집 대상 선택, 의미 해석, 적용 판단과 사용자 검토를 수행한다. 파일 검사·카드 생성·관계 투영은 결정론적으로 실행한다. 별도 모델 서버·일정 실행기·HTTP API를 추가하지 않는다.

```text
허용된 GitHub·이슈·문서·작업 결과
  → Host의 수집·통합
  → 원자료 + 위키 + 자산 설명의 Git 변경
  → 파일·참조 검사 → commit
  → 검색 → 선택한 관계·본문·코드 읽기
  → 프로젝트 적용과 근거 → 보완 후보
```

조회는 Host의 파일 검색·읽기와 위키 카탈로그를 쓴다. 파생 인덱스는 승격 조건이 충족될 때 승인된 지식 범위별로 분리해 만든다. 어느 경우든 Host가 이번 요청의 허용 출처를 먼저 결정하고, 콘텐츠에 쓰인 경로나 도구 호출 지시는 권한으로 해석하지 않는다.

## 2. 파일 계약

### 위치와 식별

```text
dev-knowledge/
  index.md
  raw/                     # 캡처한 근거·관찰·실험
  wiki/                    # 노하우와 자산 설명
  templates/               # 실제 재사용 파일
```

기존 템플릿 설명은 당장 `wiki/`로 옮기지 않는다. 파일 위치와 무관하게 안정적인 `id`로 식별한다. 모든 인덱스의 키는 `(source_alias, id)`다. `source_alias`는 선택한 저장소의 안정적인 별칭이며 로컬 절대 경로가 아니다. 외부 URL 자체를 내부 ID로 사용하지 않는다.

파일 내부 참조는 기본적으로 현재 문서 기준 상대 경로다. 기존 `resource: /templates/...`는 지식 저장소 루트 기준으로 읽는다. 읽기 전에 경로를 정규화하고 symlink를 해석해 허용 루트 밖으로 나가지 않는지 확인한다.

### 노하우 문서

기존 `type`, `title`, `description`, `tags`, `status`, `sources`를 유지한다. 새 형식을 식별하는 `knowledge_version: 1`과 다음 필드를 추가한다. 아래 예시는 실행 환경을 검증한 실제 기록이 아니다.

```yaml
knowledge_version: 1
id: worktree-runtime-isolation
type: Playbook
title: 여러 worktree의 개발 실행 격리
description: 여러 개발 인스턴스의 포트와 비동기 작업 경로를 구분한다.
tags: [worktree, development]
status: stable
adoption: candidate
applies_when:
  - 같은 프로젝트의 개발 인스턴스를 동시에 실행한다.
cautions:
  - 포트를 나눠도 작업 큐와 DB가 격리되는 것은 아니다.
aliases: [워크트리, 개발 서버 충돌]
sources: []
relations: []
```

본문은 상황, 방법, 선택 이유, 주의점, 확인 결과를 필요한 만큼 설명한다. `description`과 조건·주의점 메타데이터는 카드에 필요한 요약이며, 본문과 다른 주장을 하지 않는지 변경 시 함께 검토한다. 근거 없는 예시는 후보로만 저장하고 기본 추천에 채택 지식처럼 표시하지 않는다.

`status`는 기존 위키의 내용 상태를 유지한다. `adoption`은 `candidate`, `accepted`, `deferred`, `superseded` 중 하나이며 사용자 채택과 관련된다. 검증은 상태값 하나로 올리지 않고 아래 근거 기록으로 연결한다. `stable`은 사용자 채택이나 실제 실행 성공을 뜻하지 않는다.

### 근거와 검증

원자료는 `id`, 원본 위치, 캡처 시점, 원본 버전 또는 digest를 가진다. 같은 원본 버전의 재수집은 기존 캡처를 재사용한다. 원문 변경은 새 캡처로 남긴다.

검증 기록에는 대상 ID·내용 digest, 환경·의존 버전, 확인한 범위, 명령 또는 재현 절차, 결과(`passed`, `failed`, `inconclusive`), 실행 시점과 출력·CI·테스트 참조를 둔다. 계획만 있으면 검증 기록을 만들지 않고 위키에 예정으로 남긴다. 일부 범위의 통과는 전체 자산의 검증으로 확대하지 않는다.

채택 근거는 채택한 내용 digest, 사람의 명시 판단 위치와 시점을 연결한다. 채택 후 내용이 변경되면 이전 채택 근거는 보존하되 새 내용에 유효하다고 표시하지 않는다. 확인일·생성일·검토일을 서로 대체하지 않는다.

### 자산과 적용 기록

자산 설명은 노하우 문서의 검색 필드를 재사용하고 실제 `resource`와 종류(`file`, `bundle`, `repository`)를 추가한다. 원본 버전·경로, 필요한 구성·명령, 검증 참조를 연결한다. 로컬 Git 자산은 파일 digest와 외부 인덱스의 commit을 사용해 자기 commit SHA를 파일에 삽입하는 순환을 피한다.

프로젝트 적용 기록은 자산 ID·원본 버전, 대상 프로젝트 revision, 복사한 경로, 변경 이유·차이, 검증 참조를 보존한다. 프로젝트 evidence가 공개라 원천 정보를 담을 수 없다면 허용된 비공개 범위에 대응 관계를 기록한다. 별도 변경 없는 복사와 프로젝트 전용 변형을 구분한다.

## 3. 조회 계약

기본 조회는 새 API 없이 기존 도구로 충족한다.

| 동작 | 바인딩 |
| --- | --- |
| 정확한 문구·식별자 | Host 파일 검색 |
| 후보 탐색 | 위키 카탈로그(index.md) 읽기 후 선택한 절 읽기 |
| 근거·대체 관계 따라가기 | 프론트매터 관계와 링크 |
| 코드 근거 확인 | 기록된 commit의 파일 읽기 |
| 원문 확장 | raw/와 원본 저장소 검색 |

결과는 페이지 ID, 경로, 절, 상태, 출처 참조로 추적 가능해야 한다. 적용 전에 현재 파일을 다시 읽고 삭제된 대상을 거부한다. 조건이 맞지 않는 후보를 억지로 추천하지 않고, 부재는 부재로 보고한다.

못 찾은 질의는 위키 유지보수 관찰로 기록한다. 이 기록이 파생 인덱스의 승격 근거이며, 승격 시 검색 카드 필드·탐색 예산·반환량 제한을 그때의 실패 사례로 설계한다.

## 4. 관계 기록

관계는 지식 파일 프론트매터에 산다: 대상 ID, 종류(기획 7절), 적용 범위, 근거 위치. 대상·범위·근거가 없는 지지·반박·대체 관계는 만들지 않으며, 일반 링크는 `related_to`다. 정방향으로 기록하고 역방향 탐색에서도 원래 방향을 반환한다.

`CodeReference`는 저장소 identity, commit SHA, 경로, 선택적 심볼·범위를 기록한다. mutable 브랜치 URL은 검증 근거를 대체하지 않고, 심볼 이동을 추정해 기존 커밋 참조를 조용히 바꾸지 않는다.

그래프 DB는 승격 조건이 충족될 때 이 기록에서 결정론적으로 재생성하는 파생물이다. 노드 구성, staging, 교체 프로토콜, 장애 처리는 승격 시점의 설계 항목이며 지금 확정하지 않는다. 재구축이 LLM으로 관계를 재추출하지 않는다는 원칙만 지금 고정한다. 각 기록은 원본 문서·절·revision과 접근 경계를 가지며, 향후 어떤 인덱스도 권한 밖 노드를 거치는 경로를 반환하지 않는다.

## 5. 기존 기록 이행

- 기존 Playbook·resource 경로는 유지하고 부족한 ID만 부여한다. 별칭 변경은 기존 ID를 재발급하는 이유가 아니다.
- `status: stable`이나 과거 `verified` 날짜를 개인 채택·실행 검증으로 변환하지 않는다. 범위와 증거가 불명확하면 기존 메타데이터로 보존하고 신규 검증은 미확인으로 반환한다.
- `references/learning.md`의 `pending` 후보는 후보로 가져오며 기존 프로젝트·task·Evidence를 연결한다. dismissed·deferred는 보류 이유를 보존한다.
- 현재 사용자 편집과 수집 시작 시점의 digest가 다르면 해당 페이지를 다시 읽고 통합한다. Git 충돌을 최종 작성자의 내용으로 일괄 덮어쓰지 않는다.
- 공개 대상의 전환이나 업무 자료 이전은 실제 원격 상태와 승인된 범위를 확인한 별도 작업이다. 경로 설정만으로 쓰기 권한을 인정하지 않는다.

## 6. 구현 단위와 검증

| 순서 | 독립 결과 | 요구사항 | 검증 |
| --- | --- | --- | --- |
| 1 | 위키·근거·자산 형식, 검사와 기존 후보 읽기 | KNOW-01, 06, 08 | 중복·깨진 참조·루트 탈출·기존 상태 오해를 식별. 실제 자산 경로 보존 |
| 2 | 카탈로그·프론트매터 관계와 native 조회, 실패 관찰 기록 | KNOW-02, 03, 08 | 표본 질문의 근거 도달, 한영 혼용, 무결과 보고, 관계 링크 탐색, miss가 관찰로 남음 |
| 3 | GitHub 근거와 자산 적용 기록 | KNOW-04, 05 | 고정 commit, 현재 경로 변경, 단일 파일·묶음·저장소 변형, 사용 이력 |
| 4 | Host 수집·채택·지정 챌린지와 재사용 회수 | KNOW-01, 06, 07 | 사용자 수정 보존, 미실행 계획 구별, 실제 작업 한 건의 결과 회수 |

파생 인덱스(의미 검색, 그래프 DB)는 이 표의 단위가 아니다. 2번이 기록한 실패 관찰이 승격 조건을 충족하면 그때 별도 결정과 설계로 추가한다.

각 작업은 선행 결과의 계약을 읽되 ADR의 배경을 본문에 복사하지 않는다. 코드 경로와 검증 명령은 해당 작업을 만들 때 존재를 확인해 확정한다. 이 설계는 Rust 계획 검증기에 새 검색 기능을 모두 넣으라고 요구하지 않는다. 현재 검증기와 새 파일 검사 코드가 공유할 책임만 추출한다.

표본은 기획의 상황 사례와 그 변형으로 구성하고 기대 ID·근거를 미리 정한다. 테스트 데이터는 공개 또는 합성 자료로 만들며 업무 원문을 테스트 fixture에 복제하지 않는다. 결정론적 검사는 의미의 정확성을 대신하지 않으므로 근거의 지지 여부와 적용 조건은 별도로 검토한다.

검색 평가는 표본 질문이 native 조회만으로 근거에 도달하는지 기록하고, 실패를 관찰로 남긴다. 파생 인덱스를 승격하면 같은 표본으로 전후를 비교한다. 적은 호출만으로 품질 개선을 주장하지 않는다. 요구사항 ID와 기획 revision을 구현·실패·수정 근거에 연결해 기획 작성법 자체도 평가한다.

## 구현 착수 전 남은 선택

- AUT-1·AUT-2·AUT-3의 승인과 프로젝트 실행 정책에 필요한 변경.
- 실제 지식 읽기·쓰기 대상, 출처별 접근 범위와 첫 재사용 작업.
- 파생 인덱스 승격 조건의 판정 방식: 어떤 실패 관찰이 몇 건이면 승격을 검토하는지. QMD·Neo4j 적합성 확인은 그 승격이 결정된 뒤의 일이다.

다음 작업은 1번 계약을 작은 fixture로 검증하는 구현 명세 작성이다. DB나 검색 서비스 설치, 광범위한 원자료 수집을 먼저 시작하지 않는다.
