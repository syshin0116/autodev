# 개발 지식과 재사용 자산 관리 기획

작성일: 2026-09-10 · 상태: 기획 초안

후속 문서: [구현 설계](knowledge-implementation-design.md)

프로젝트 경험과 외부 자료에서 개발 노하우를 추출하고, 비교·검증하며 다듬어 다음 프로젝트에 적합한 방법과 재사용 자산을 제공한다. 사용자가 직접 지식을 수정하고 자신의 기본 개발 방식으로 채택할 수 있어야 한다.

이 문서는 제품의 사용 흐름, 정보 구조, 저장 책임, 검색 방식과 첫 버전 범위를 정의한다. 기존 [LLM Wiki 구현 제안](40-llm-wiki.md)의 확장 요구사항이며, 현재 승인된 [프로젝트 계약](project-overview.md)이나 실행 권한을 변경하지 않는다. 구현 제안과 다른 부분은 이 기획을 기준으로 후속 설계에서 정합화한다.

## 1. 해결할 문제

- 프로젝트에서 얻은 선택 이유, 실패 경험, 검증 방법이 코드·PR·이슈·대화에 흩어져 다음 작업에서 다시 조사한다.
- 좋은 설정을 복사해도 그 설정이 성립하는 전제와 주의점은 함께 전달되지 않는다.
- CI 파일 하나부터 전체 보일러플레이트까지 재사용 규모가 다르다. 기술 조합의 모든 변형을 미리 관리하려 하면 유지 부담이 커진다.
- 외부 방법을 수집해도 내 방식과 같은 조건에서 비교하고 채택하는 과정이 없다.
- 검색 결과에 긴 문서와 코드를 한꺼번에 넣으면 후보 선택에 불필요한 내용까지 읽게 된다.

첫 사용자는 여러 개인·업무 프로젝트를 오가며 개발하는 저장소 소유자다. 지식을 작성·검토하는 경험과 개발 중 지식을 찾아 사용하는 경험을 함께 제공한다.

## 2. 지식의 기본 단위

독립적으로 다시 사용할 수 있는 상황과 방법을 중심으로 정리한다. 작업 하나나 문서 하나를 기계적으로 지식 하나로 변환하지 않는다. 한 상황에 여러 방법이 연결될 수 있고, 한 방법을 여러 프로젝트가 뒷받침하거나 반박할 수 있다.

| 항목 | 내용 |
| --- | --- |
| 상황 | 증상, 목표, 환경, 제약 등 이 지식이 필요한 조건 |
| 방법 | 실제로 적용할 절차나 구성 |
| 선택 이유 | 비교한 대안, 선택 기준, 감수한 비용 |
| 주의점 | 필요한 전제, 실패 조건, 부작용, 적용 범위 밖의 경우 |
| 확인 결과 | 실험 환경·버전·범위·결과와 아직 확인하지 못한 부분 |
| 연결 | 근거, 코드, 테스트, PR, 재사용 파일, 대안과 적용 사례 |

확인하지 않은 항목을 LLM이 채우지 않는다. 단순 관찰은 후보로 보존하고, 비교하지 않은 대안이나 측정하지 않은 효과를 만들지 않는다. 근거의 내용과 새롭게 일반화한 해석을 구별한다.

### 실제 기록에서 확인한 추출 후보

| 상황 | 방법·노하우 후보 | 주의점 | 원천 |
| --- | --- | --- | --- |
| 에이전트가 문서 검색 결과를 과도하게 읽음 | 짧은 후보 검색과 선택한 원문 읽기를 분리 | 상세 읽기의 범위와 반환량도 제한해야 함 | SKAX 문서 검색 ADR, 아래 출처 참조 |
| 테스트가 단독으로 통과하지만 전체 실행에서 순서에 따라 실패 | 실행 목록을 이분 탐색해 공유 상태 오염원을 찾음 | 실패가 드러난 테스트와 원인을 만든 테스트가 다를 수 있음 | SKAX CI 최적화 플레이북 |
| CI가 느려 병렬도를 바꾸려 함 | 실행 시간·대기 시간·자원 경합을 구분해 비교 | 로컬과 CI 수치, CPU 시간과 전체 완료 시간을 혼합하지 않음 | SKAX CI 최적화 플레이북 |
| 여러 worktree에서 개발 서버를 동시 실행 | 포트·작업 큐·채널을 구분 | 포트 격리만으로 비동기 경로와 DB까지 격리됐다고 가정하지 않음 | Finance Makefile과 포트 스크립트 |
| 위키에 출처와 날짜가 있어 검증된 정보로 표시 | 수집·추출·검토·게시 상태를 분리 | 일부 근거 검토를 페이지 전체의 검증으로 확대하지 않음 | Finance 위키 계약과 FIN-124 관련 변경 |
| 이슈가 완료 상태지만 검증 근거가 불완전 | 구현·머지·자동 검사·사용자 흐름 확인을 구분 | 완료 라벨만으로 지식을 검증됨 처리하지 않음 | Linear RE-630 |

이 표는 문서·코드·이슈를 읽어 만든 후보다. 이번 기획에서 테스트를 재실행하거나 현재 배포 동작을 확인하지 않았다. 공동 작업에서 나온 경험은 원저자와 기여 출처를 보존하고 개인의 독자적인 성과로 재표기하지 않는다.

## 3. 핵심 사용 흐름

### 프로젝트에서 추출

1. 사용자가 저장소, PR, 이슈, 문서 또는 작업 결과를 선택한다.
2. 관련 변경 이유, 코드, 검사 결과와 후속 정정을 읽는다. 이슈에 적힌 계획과 실제 구현 결과를 구별한다.
3. 상황·방법·주의점을 추출하고 기존 지식에서 같은 문제와 대안을 찾는다.
4. 신규 후보, 기존 지식 보완, 반박, 중복, 프로젝트 한정 기록으로 구분한다.
5. 근거와 함께 검토할 변경안을 제시한다. 같은 내용을 반복 수집해 새 지식이 늘어나지 않게 한다.

코드 구성 자체, 시행착오, 효과 없는 실험, 사용자의 수정과 보류 이유도 입력이다. 원자료 수집기는 만들지 않는다. Agent Host의 세션 기록, git 이력, PR·이슈·CI 기록이 이미 실행 관찰의 원자료이며 추출은 거기서 읽는다. 대화 전체를 저장할 필요는 없으며, 유용한 관찰과 지속적으로 확인 가능한 근거만 남긴다.

### 개발에 적용

검색과 지식 컴파일은 계획 단계의 일이다. 실행 에이전트는 계획이 태스크 입력에 컴파일해 넣은 지식만 받고 위키를 직접 조회하지 않는다.

1. 현재 문제와 프로젝트 조건으로 작은 검색 후보를 찾는다.
2. 적용 조건과 핵심 주의점을 비교하고 필요한 상세 설명을 읽는다.
3. 실제 코드·템플릿을 확인해 그대로 사용할 부분, 수정할 부분, 검증할 부분을 정한다.
4. 프로젝트의 승인 범위 안에서 적용하고 결과를 기록한다.
5. 새로 확인한 조건과 실패를 기존 지식에 연결한다. 자산 개선은 별도 후보로 제안한다.

### 직접 수정

사용자는 위키와 재사용 파일을 직접 수정하거나 대화로 변경을 요청할 수 있다. 후속 수집은 현재 사용자의 편집을 기준으로 통합하고, 충돌한 주장을 조용히 덮어쓰지 않는다. 개인 선호와 효과에 대한 주장을 구분한다. 선호의 채택이 성능이나 품질 개선의 증거는 아니다.

### 외부 챌린지

1. 사용자가 지정한 지식, 최근 실패한 방법, 오래된 검증을 대상으로 선택한다.
2. 공식 자료·코드·커뮤니티에서 대안과 반례를 조사한다.
3. 기존 방식과 비교할 조건, 기대 효과, 비용, 작은 실험을 제안한다.
4. 실험 결과에 따라 유지, 적용 범위 수정, 대체, 보류를 기록한다.

커뮤니티 글은 실험의 단서이며 그 자체로 개인 환경의 우월성을 증명하지 않는다. 같은 원문을 재인용한 여러 글이나 저장된 LLM 답변을 독립된 검증 근거로 세지 않는다. 정기 실행은 후속 범위에서 대상·주기·비용 상한을 정해 도입한다.

## 4. 정보별 저장 책임

| 정보 | 원본 위치 | 저장 내용 |
| --- | --- | --- |
| 원자료·관찰·실험 | 허용된 지식 저장소의 `raw/` 또는 원본 시스템 | 출처, 버전, 관찰과 결과. 필요한 범위만 캡처 |
| 개발 노하우·비교·챌린지 | `wiki/`의 Markdown | 상황·방법·이유·주의점·확인 결과와 관계 메타데이터 |
| 템플릿·설정 묶음 | `templates/`의 실제 파일 | CI, 스크립트, 여러 파일 구성. 사용 문서는 위키에서 연결 |
| 보일러플레이트 | 독립 Git 저장소 또는 기존 저장소 | 실행 가능한 프로젝트. 지식 저장소에 전체 코드를 중복 복제하지 않음 |
| 자산 설명 | 위키의 자산 문서 | 적용 조건, 구성, 사용법, 검증한 버전, 원본 위치 |
| 프로젝트 적용 기록 | 프로젝트 evidence 또는 허용된 지식 저장소 | 가져온 자산 버전, 수정 내용, 검사 결과. 공개 범위에 맞춰 연결 |
| 관계 | 지식 파일의 프론트매터 | 대상, 종류, 적용 범위, 근거 위치. 파생 인덱스의 재료 |

LLM 위키는 후보와 채택한 지식을 모두 유지한다. 단기·장기 구분은 지식의 성숙도로 표현하며 저장 기술과 일치시키지 않는다.

관계의 원본은 파일 메타데이터다. 파생 인덱스(의미 검색, 그래프)는 6절의 승격 조건을 충족할 때 여기서 재생성하며, 인덱스에서만 관계를 수정하는 별도 경로는 만들지 않는다.

기존 `dev-knowledge` 구조와 메타데이터를 우선 재사용한다. 회사 자료와 개인 자료는 승인된 저장·검색 범위를 유지한다. 통합 조회 가능 여부와 개인 저장소로 복사 가능 여부는 별개이며, 관계명·코드 링크와 향후의 파생 인덱스도 원천의 접근 범위를 따른다.

## 5. 재사용 자산과 조합 관리

파일 하나, 여러 파일 묶음, 전체 보일러플레이트를 모두 지원한다. 크기와 무관하게 원본 위치·버전, 적용 조건, 사용 방법, 확인한 검사와 의존 구성을 연결한다. 단일 CI 파일에도 실행 명령이나 환경 설정 의존성이 있을 수 있다.

예를 들어 aegra + Postgres + Redis + Next.js 구성을 Vite 기반 프로젝트에 사용하려면:

1. 기존 구성이 유용한 출발점인지 확인한다.
2. 프런트엔드가 맡던 인증·서버 처리·빌드·배포 역할을 확인한다.
3. 필요한 부분을 프로젝트 안에서 변경하고 연결 경계를 검증한다.
4. 교체 경험은 위키에 남긴다. 반복 사용 가치가 확인되면 별도 자산으로 승격한다.

모든 조합을 미리 생성하지 않는다. 한 번의 변형은 프로젝트에 남겨도 되며, 공통 템플릿의 옵션으로 흡수할 필요가 없다. `구성요소` 관계는 실제 포함 관계를 뜻하며 다른 조합과의 호환성을 증명하지 않는다.

초기 적용 방식은 버전이 명시된 복사와 프로젝트별 수정이다. 원본 자산 변경이 사용 중인 프로젝트를 자동 수정하지 않는다. 사용 관계를 통해 영향 후보와 변경 비교를 제시한다.

## 6. 검색: 있는 것부터, 승격 조건부로

기본 조회는 Agent Host의 파일 검색·읽기와 위키 카탈로그다. 코퍼스가 거의 없는 상태에서 검색 카드·탐색 예산·전용 인덱스를 먼저 만들면 없는 문제를 위한 유지비가 생긴다. 대신 못 찾은 질의를 유지보수 관찰로 기록하고, 그 기록이 승격 조건이 된다.

| 파생 인덱스 | 승격 조건 | 첫 후보 |
| --- | --- | --- |
| 의미 검색 | 파일 검색 miss가 기록으로 쌓임(한국어 질의 포함) | QMD, 한국어 품질·로컬 자원 확인 후 |
| 관계 질의 | 다단계 관계 질문이 실제 작업에서 반복 | 프론트매터 관계 위의 로컬 그래프 |

검색 카드의 필드 설계와 탐색 예산은 의미 검색을 승격할 때 함께 정한다. 파일명·함수명·오류 문구를 지정한 질문은 지금도 해당 코드·원문 검색으로 바로 진입한다.

## 7. 관계 기록과 GitHub 연결

관계는 지금부터 지식 파일의 프론트매터에 원본 ID, 대상 ID, 종류, 적용 범위, 근거 위치와 함께 기록한다. 그래프 DB는 이 기록에서 재생성할 수 있는 파생물이며, 다단계 관계 질의가 실제로 필요해질 때 승격한다. 승격 전에는 링크를 직접 따라간다.

| 관계 | 방향과 의미 |
| --- | --- |
| `supports` / `contradicts` | 근거·지식 → 지식. 명시한 조건 안에서 뒷받침하거나 반박 |
| `supersedes` | 새 지식·자산 → 이전 항목. 대체되는 범위를 명시 |
| `alternative_to` | 방법 → 다른 방법. 대안이며 우열·동등성 보장은 아님 |
| `implemented_by` | 지식 → 코드 참조·자산. 해당 방법의 구현 사례 |
| `uses` | 프로젝트 적용 기록 → 자산의 특정 버전 |
| `contains` | 보일러플레이트 → 구성요소. 실제 포함 관계 |
| `cites` / `related_to` | 인용·일반 연결. 지지나 검증으로 승격하지 않음 |

관계는 원본 ID, 대상 ID, 관계 종류, 적용 범위와 근거 위치를 유지한다. 검증 관계에는 검사 대상의 정확한 버전과 검증 범위를 연결한다. 관계의 범위는 연결된 노드 전체로 자동 확대하지 않는다.

GitHub 코드 참조에는 저장소, 커밋 SHA, 경로, 필요한 경우 심볼과 줄 범위를 기록한다. 두 링크를 구분한다.

- **근거 링크:** 검증 당시 커밋에 고정한 코드·테스트·PR 변경과 CI 결과.
- **현재 위치:** 현재 브랜치의 코드 위치. 이동·삭제·변경 여부를 확인하는 용도.

심볼이나 파일의 이동을 자동으로 추정해 근거를 교체하지 않는다. 연결이 끊기면 과거 근거를 보존하고 현재 위치 확인을 요청하거나 재탐색한다. PR 머지와 CI 성공은 해당 검사 범위의 증거이며, 배포 확인이나 일반적인 우월성을 뜻하지 않는다.

## 8. 검증·채택·재검토

| 구분 | 기록할 상태 |
| --- | --- |
| 채택 | 후보 / 채택 / 보류 / 대체됨 |
| 검증 | 미검증 / 특정 환경과 버전에서 확인한 결과 |
| 재검토 | 알려진 충돌, 변경된 근거, 오래된 의존 조건 |

검증 여부는 단일 점수보다 근거와 범위로 표현한다. 직접 수정을 포함한 모든 변경은 출처와 이유를 보존한다. 새 반박은 기존 지식을 삭제하지 않고 연결하며, 해결되지 않은 충돌이 있으면 기본 추천에 함께 표시한다.

초기에는 허용된 쓰기 범위 안에서 수집·후보 작성·근거 연결·인덱스 갱신을 수행한다. 개인 기본값으로의 채택과 공통 자산 변경은 사용자가 검토한다. 기존 세션에서 승인한 범위는 반복 확인하지 않는다. 프로젝트 실행 권한이나 ADR 승인 상태는 지식으로부터 추론하지 않는다.

## 9. 첫 버전과 완료 기준

첫 버전은 파일과 위키만으로 추출, 검색, 적용, 회수의 한 순환을 완성한다. 별도 대시보드 대신 기존 Agent Host의 대화와 파일 검토를 사용한다. 그래프 제품·검색 엔진은 이 순환에서 기록된 실패가 승격 조건을 충족할 때 선택한다.

| 단계 | 범위 | 완료 기준 |
| --- | --- | --- |
| 표본 추출 | 허용된 SKAX·Finance 기록에서 약 10개 후보 작성 | 상황·방법·주의점·출처를 확인할 수 있고 계획과 실적을 구별 |
| 저장과 연결 | 위키, CI 파일 또는 설정 묶음, 보일러플레이트 참조, 프론트매터 관계 | 관계만으로 페이지 간 근거·대체 탐색이 가능 |
| 검색 | 파일 검색, 카탈로그, 관계 링크, 원문 확장 | 표본 질문에서 적합한 근거까지 도달하고, 못 찾은 질의가 관찰로 기록됨 |
| 실제 재사용 | 지정한 프로젝트 작업 한 건에 지식·자산 적용 | 사용 버전·수정점·검사 결과를 연결하고 결과에서 보완 후보 생성 |
| 지정 챌린지 | 지식 한 건의 외부 대안 조사와 비교 계획 | 비교 조건과 필요한 검증을 제시. 실험하지 않은 대안을 검증됨으로 표시하지 않음 |

검색 평가는 표본마다 기대하는 지식과 근거를 먼저 정한다. 상황 질문, 한국어·영문 혼용, 정확한 코드 이름, 반박·영향 탐색, 해당 지식이 없는 질문을 포함한다. 적합한 후보의 상위 노출, 근거 도달 여부, 읽은 내용량, 도구 호출 수를 기록해 파일 전체 검색 기준과 비교한다. 고정 숫자를 맞추려고 주의점이나 근거를 누락하지 않는다.

추가 확인 사례:

- 위키에 없는 오류 문구를 원문 확장 검색으로 찾는다.
- `Done` 이슈의 미완료 검증과 `proposed` ADR의 채택 표현을 그대로 검증·승인으로 해석하지 않는다.
- 코드 변경·삭제를 감지하며 과거 커밋 근거는 보존한다.
- 수집 실패나 충돌한 편집이 마지막 정상 지식과 사용자의 수정을 덮어쓰지 않는다.
- 같은 자료를 다시 수집해도 중복 페이지·근거·관계가 늘어나지 않는다.
- 접근할 수 없는 원천의 설명·관계·링크가 다른 범위의 검색 결과에 노출되지 않는다.

후속 범위는 주기적인 외부 챌린지, GitHub 변경 감지, 여러 프로젝트의 개선 제안이다. 모든 기술 조합의 자동 생성, 사용 프로젝트 일괄 갱신, 지속 실행하는 자체 에이전트 서버는 첫 버전에 포함하지 않는다.

## 10. 구현 전에 확정할 경계

- 실제 읽기·쓰기 대상과 개인·업무 지식의 접근 범위. 저장소 공개 여부를 확인한 뒤 자료를 캡처한다.
- 기존 자산과 메타데이터를 유지하는 이행 방식.
- 첫 재사용 대상 프로젝트와 검증 작업, 외부 챌린지의 조사 범위·비용.

Kaneo와 Linear의 태스크·ADR은 원본 시스템의 권한과 상태를 유지한다. 지식 저장소에 승인 상태를 새로 만들어 원본을 대체하지 않는다. 프로젝트 표본 조사 당시 Finance의 Kaneo 기록은 직접 조회하지 못했다. 이후 autodev의 Kaneo 연결과 ADR 조회·반영을 확인했다.

### Kaneo 결정 기록 연결

| 기록 | 이 기획에서 다루는 결정 |
| --- | --- |
| AUT-1 | 상황·방법·주의점 중심 지식, 검증과 채택의 구분, 기획 작성법을 포함한 학습 |
| AUT-2 | 하네스 native 조회 우선, 파생 인덱스의 승격 조건, GitHub 버전 근거 |
| AUT-3 | 재사용 자산의 버전 지정 복사와 프로젝트별 수정 |

AUT-1·AUT-2의 기존 초안을 보완하고 AUT-3을 새 초안으로 연결했다. 현재 승인 여부와 결정 본문은 Kaneo에서 확인한다. 이 연결 자체가 결정 승인이나 구현 착수를 뜻하지 않는다.

## 11. LLM 구현으로 이어지는 요구사항

구현자는 이 문서에서 사용자 의도와 관찰 가능한 완료 조건을 읽고, 필요한 절과 원천만 따라가야 한다. 기능별로 별도 설명을 복제하지 않고 아래 ID로 기획, 구현 작업, 코드와 검증 결과를 연결한다. 제품 기획만으로 미정인 저장소·인터페이스·권한을 임의 확정하지 않는다.

| ID | 요구사항과 문서 위치 | 검증 시나리오 |
| --- | --- | --- |
| KNOW-01 | 근거가 있는 상황·방법·주의점 추출, 2·3절 | 같은 PR과 이슈를 두 번 읽어도 동일 후보를 보완하며 중복 생성하지 않는다. 미실행 계획은 실험 결과에 포함하지 않는다. |
| KNOW-02 | native 우선 조회와 승격 조건, 6절 | 파일 검색·카탈로그·관계 링크로 표본 질문의 근거에 도달한다. 못 찾은 질의는 관찰로 기록되어 승격 판단의 입력이 된다. 후보가 없으면 부재를 알린다. |
| KNOW-03 | 프론트매터 관계 기록과 탐색, 7절 | 반박 근거에서 영향을 받는 지식과 사용 자산으로 링크를 따라 이동한다. 관계는 대상·범위·근거 없이 만들지 않으며, 승격 시 인덱스는 파일에서 재생성된다. |
| KNOW-04 | 버전이 고정된 코드·검증 연결, 7절 | 현재 브랜치의 파일을 변경해도 과거 근거 링크는 동일한 코드를 가리킨다. 현재 위치의 삭제는 끊어진 참조로 표시한다. |
| KNOW-05 | 자산 적용과 조합 변형, 5절 | 보일러플레이트 일부를 교체하면 수정점과 확인 결과를 기록한다. 검증하지 않은 새 조합을 호환됨으로 표시하지 않는다. |
| KNOW-06 | 사용자 수정과 신뢰 상태 보존, 3·8절 | 사용자가 수정한 주장과 새 자료가 충돌하면 두 근거를 보존한다. 검사 통과나 완료 라벨이 개인 채택을 대신하지 않는다. |
| KNOW-07 | 외부 챌린지와 결과 회수, 3절 | 대안 조사만 수행한 결과는 후보로 남는다. 비교 실험 이후에만 검증 범위와 결과를 연결한다. |
| KNOW-08 | 접근 범위와 갱신 실패 처리, 4·7절 | 권한 밖의 원천은 검색 결과와 관계에서도 제외한다. 갱신 실패 시 정상 원본을 유지하고 오래된 조회 결과를 구분한다. |

이 시나리오는 인수 기준이며 테스트 파일이나 새 API를 요구하는 것은 아니다. 후속 설계에서 기존 도구와 저장소 구조를 조사해 가장 작은 구현 단위와 검증 방법에 배정한다.

### 구현 작업으로 넘길 때

작업 하나에는 해당 요구사항 ID와 사용자 결과, 읽어야 할 정본, 변경할 기존 코드 경계, 입력·출력·실패 처리, 검증 방법을 연결한다. 이 문서에 없는 구현 세부사항은 코드 조사와 후속 설계에서 확정한다. 테스트 명령과 코드 경로는 존재를 확인한 뒤 기재한다.

예를 들어 KNOW-02를 구현할 때는 다음 계약을 구체화해야 한다.

- 입력: 질문, 프로젝트 조건, 접근 가능한 지식 범위, 탐색 예산.
- 출력: 안정적인 후보 ID, 상황·방법 요약, 적용 조건과 상태, 원본 버전, 상세 참조. 기본 조회 결과에 전체 코드나 실험 로그를 넣지 않는다.
- 실패·예외: 무결과, 오래된 인덱스, 삭제된 상세 참조, 접근 불가, 예산 소진을 구별한다. 접근 불가 자료의 존재나 내용을 응답에 드러내지 않는다.
- 검증: 같은 상황의 유사하지만 부적합한 후보를 함께 넣고 적합한 후보와 근거에 도달하는지 확인한다. 원문에만 있는 오류 문구는 확장 검색으로 찾는지 확인한다.

기획의 변경은 관련 요구사항 ID를 통해 작업과 검증에 반영한다. 구현 중 발견한 새로운 제약은 이유와 함께 기획·설계에 되돌린다. 작업 상태나 코드 작성 완료만으로 제품 요구사항을 완료 처리하지 않는다.

## 12. 기획 작성법 자체의 학습

기획, 작업 분할, 구현 지시, 리뷰·검증 방법도 개발 노하우의 대상이다. 이번 문서 역시 실제 구현 결과로 평가할 후보이며, 요구사항 ID나 문서 형식만으로 구현 품질이 개선됐다고 주장하지 않는다.

| 항목 | 이번에 검증할 작성법 후보 |
| --- | --- |
| 상황 | LLM이 기획을 읽고 구현하지만 예외를 임의로 정하거나 완료 범위를 다르게 해석함 |
| 방법 | 사용자 결과를 요구사항 ID로 식별하고, 정상 흐름·실패 처리·인수 기준·코드와 근거 링크를 연결 |
| 선택 이유 | 구현자가 필요한 결정을 찾고, 검토자가 요구사항 누락과 구현 차이를 확인할 수 있게 함 |
| 주의점 | 기획에 상세 코드를 미리 고정하거나 같은 설명을 여러 문서에 복제하면 변경 비용과 모순이 늘어남. 초기의 미정 사항은 명시적으로 유지 |
| 확인 결과 | 미검증. 이번 오토데브 구현에서 수집할 예정 |
| 연결 | 기획의 정확한 버전 → 구현 작업 → PR·수정 이력 → 테스트·사용 확인 → 기획 수정 |

구현하면서 다음 관찰을 작업 근거에 남긴다. 별도 상시 보고서를 늘리지 않는다.

- **추가 질문:** 기획의 누락 때문인지, 구현 중 새 사실이 드러났기 때문인지 구분한다. 질문 수가 적다는 사실만으로 좋은 기획이라 판단하지 않는다.
- **재작업:** 어떤 문구·누락·충돌이 잘못된 구현을 유발했는지 구체적인 요구사항과 변경으로 연결한다.
- **결함과 누락:** 정상 흐름만 구현했는지, 실패·권한·버전 경계를 놓쳤는지 확인한다.
- **탐색 부담:** 필요한 근거를 찾기 위해 어느 문서·코드까지 읽었고 어떤 링크가 빠졌는지 기록한다.
- **검증 가능성:** 인수 기준으로 결과를 판정할 수 있었는지, 뒤늦게 완료 기준을 새로 만들어야 했는지 확인한다.

가령 구현이 현재 브랜치 링크만 저장했다면 KNOW-04의 요구가 누락됐는지, 작업에 전달되지 않았는지, 명시됐는데 구현에서 놓쳤는지를 나눈다. 원인을 확인한 뒤 해당 기획 작성법이나 작업 전달 방식을 보완한다. 문서 분량을 늘리는 것을 기본 해결책으로 삼지 않는다.

그 결과를 다시 상황·방법·주의점 형태로 축적한다. 다른 작업이나 프로젝트에서도 재사용한 근거가 쌓이면 개인 기획 템플릿으로 채택한다. LLM·도구·작업 난이도가 다른 사례를 같은 조건의 비교로 취급하지 않는다.
